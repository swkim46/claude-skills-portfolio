# Consulting DOCX Report

> ### ▶ 단계 게이트 (빠른 바닥은 인라인, 빡빡한 가이드 심판은 비동기 gate-audit)
> hook 차단 환경의 강제 레버. 헬퍼 `SG` = `python3 <REPO>/.claude/skills/_stepgate/stepgate.py`.
> **★ 동시 작업 격리** — 이 워크플로의 *모든* SG 호출(form·judge·resolve)에 **같은 `dir=<과제폴더 절대경로>`**를 붙인다(다른 과제=다른 폴더→자동 격리, 같은 폴더 다중 산출물은 `deliverable=`로 구분). 누락 시 form↔judge 키가 갈려 오작동.
> **① 빌드 직후(바닥 ~5s)**: `SG form research-docx publish dir=<과제폴더>` → 산출물 열고 **정직히** 답(합격 기준 비공개·**표현이 회차마다 뒤집히니 지난 답을 재사용하지 말고 이번 문구를 그대로 읽고 답할 것**) → `SG judge research-docx publish <id>=<값> … deliverable=<docx 절대경로> dir=<과제폴더>`. **GATE PASS**면 바닥 통과 → PASS 직후 FIRE 블록으로 **백그라운드 감사 에이전트(general-purpose) 발사(run_in_background)·즉시 다음 작업**(대기 금지).
> **② 저장·보고 직전(해소)**: `SG resolve research-docx deliverable=<docx 절대경로> dir=<과제폴더>` → **RESOLVE PASS 아니면 'done' 금지**(HOLD=동기 드레인·FAIL=새 vN_M 수정·재감사).
> **★ 노출 = 게이트 (미루기 금지).** 사용자에게 *보여주거나 보고하는* 모든 docx 버전(반복·중간본 포함)은 *그 버전에서* publish→async audit→resolve를 통과한 뒤에만 제시한다 — '내용이 더 바뀌니 최종본에서 일괄 게이트'로 미루면 *미감사 버전*(질문형 제목·구어·무근거 분석)이 그대로 노출된다. 빠른 반복은 *노출 안 하는* `_working.docx`로, 사용자에게 내보내는 *순간* `vN_M`+게이트.
> 흐름: **publish 바닥** → 비동기 lens 감사(audit_rubrics) → **resolve**. 봉인 루브릭(rubrics/) 직접 열람 금지(감사됨). 상세: `skill-maintainer` 〈단계 게이트 프로토콜〉.
> `<REPO>` = 이 저장소를 클론한 **절대경로**(문서상 표기). `dir=`·`deliverable=`은 절대경로여야 하므로 호출할 때 실제 경로로 치환한다.

검증 완료된 리서치/분석 내용을 **컨설팅 하우스스타일 Word 보고서**로 포매팅하는 스킬. 본 스킬에 **동봉된** 하우스스타일 정본 `references/docx_consulting_report_guide.md`를 준거로 하며(외부 경로 의존 없음 — **단독 실행**), 재사용 헬퍼는 `scripts/docx_helpers.py`에 있다.

**경계(boundary):** 이 스킬은 **포매팅 스킬**이다. 리서치·출처 검증·분석을 하지 않는다 — 그건 `research-verified`. 엑셀 산출물은 `research-organizer`. 이 스킬은 **이미 검증된 내용을 .docx로** 만든다. 입력 내용이 미검증이면 먼저 research-verified로 검증을 받도록 안내한다.

**1 스킬 호출 = 1 산출물.** 같은 작업을 반복하면 새 버전(`_v2`/`_v3`)으로 발행하고 기존 파일을 덮어쓰지 않는다.

시작 전 동봉된 `references/docx_consulting_report_guide.md` 전문을 읽고(§1~§10), 아래 규칙을 적용한다. (본문의 `(가이드 §N)`은 이 동봉 가이드를, `(방법론 X-N)`은 `research-verified` 스킬 동봉 검증 방법론의 해당 항목을 가리키는 앵커다.)

## 시작 전 확인

사용자 메시지에 이미 답이 있으면 재질문하지 않는다.

- **작업/주제는?** **소스 내용은?**(검증된 .md 마스터·붙여넣기 텍스트·링크표) 있으면 먼저 읽는다.
- **신규 vs 기존 편집?** 기존 .docx 편집이면 그 파일의 폰트·구조 관례를 보존하고, **사용자 수동 편집을 diff로 확인**해 덮어쓰지 않는다(가이드 §10 / 방법론 E-7).
- **문서 유형?** 6-A 분석보고서(현황→Bear/Bull→전망) vs 6-B 인사이트 전달용(6-B-1 리서치 정리 / 6-B-2 인사이트 분석). 가이드 §6 참조.
- **출처 표기?** 본문 라벨(R/C/A/N + 분석보강 O) ↔ 출처 섹션 1:1. 라벨·URL은 SRC dict로 관리.

소스가 불완전하거나 출처가 없으면 **날조 금지** — `[출처 확인 필요]` 플레이스홀더를 남기고 사용자에게 알린다.

## 빌드 패턴

`scripts/docx_helpers.py`를 import해 셀을 채운다(헬퍼 docstring에 시그니처). 핵심:

```python
import sys; sys.path.insert(0, r"<REPO>/.claude/skills/research-docx/scripts")
import docx_helpers as D

doc = D.new_doc()                              # 맑은 고딕 EastAsia, 여백 세팅
SRC = {                                        # 라벨→URL 단일 출처 dict
    'R1': 'https://www.imf.org/...',
    'C1': 'https://www.worldbank.org/...',
    'N4': 'https://www.ojk.go.id/...',
}
D.title(doc, "인도네시아 경제·금융 리서치", sub="중기(3~5년) 전망", note="작성: 2026-06-08")
D.H1(doc, "1. 현황 — 기대 대비 실제")
D.B(doc, [("인구(2025): ", True), ("약 284M명, 세계 4위", False)], refs=D.R(SRC, 'C1'))
D.Q(doc, "Indonesia ... seventh-largest economy by 2030", 'R1', SRC['R1'])   # verbatim 인용
D.TABLE(doc,
        ["지표", "값", "출처"],
        [["은행 NIM", "4.54%", "N4"], ["신용/GDP", "약 35%", "C1·R1"]],
        src_col=2, SRC=SRC)                    # ★ 표 출처 열 라벨 → 각각 클릭 하이퍼링크
D.src_section(doc, "출처", [("R1","IMF WEO 2025","R1"), ("C1","World Bank","C1")], SRC)

# ★ 저장은 반드시 save_versioned로 — 고정 파일명 doc.save() 금지(재빌드 시 덮어써짐).
# 폴더 스캔→다음 vN_M 자동 발행·기존 파일 있으면 예외(clobber-proof)·직전 minor 자동 이관.
# major/minor는 사람이 판단(기본 minor / 구조·결론·핵심수치 변경 시 major=True) — 번호·이동은 도구가.
path = D.save_versioned(doc, r"<REPO>\인도네시아", "research_인도네시아_경제금융")   # doc.save 포함·경로 반환
print(D.verify(path))                          # {'external_links': N, 'unique_urls': M}
```

빌드 실행: `& "python3" build_docx.py` (python이 PATH에 없을 수 있음).

## 필수 규칙 (가이드 §7·§8·§10 + 방법론 Part E)

### 1) 출처 하이퍼링크 — 본문과 표 안 모두 (가이드 §10·§4)
- 본문 인용 라벨 `[R1]`은 `refs=D.R(SRC,...)`로 **클릭 가능 링크**. 평문 `[R1]` 금지.
- **표 안 출처 셀도 반드시 하이퍼링크** — `TABLE(..., src_col=N, SRC=SRC)`. `C1·R2 / O4`처럼 한 셀에 여러 라벨이면 각 라벨이 개별 링크, 구분자는 평문(`_fill_src_cell` 자동 처리).
- 모든 링크는 **접속 가능**해야 함 — 빌드 전 원문 fetch로 검증(봇 차단 403/000/Cloudflare 챌린지는 *죽은 링크도 유료도 아님* — 브라우저/curl로 확인, E-1). 빌드 후 `D.verify(path)`로 external_links 수 확인.
- **★ 출처를 *지목*한 주장은 그 출처 링크 필수(named-source-without-link 금지).** "○○(매체·보고서)에 따르면 …"처럼 특정 출처를 지명한 load-bearing 문장은 그 출처의 **클릭 링크를 반드시 동반**한다 — 본문이 미검증·봇차단·페이월이어도 *링크는 제공*(독자가 직접 판단). '미검증/한계'라는 이유로 링크를 생략하지 말 것. *실사례: '○○에 보도됨'이라 써놓고 URL 없이 발행 → 출처표기 누락.* cf. research-source-check 1-bis.

### 2) 명사형·전문 워딩 (가이드 §7)
- 문장 종결은 **명사형으로 통일**(~함/~임/~됨/~음). '~다'와 명사형 혼용 금지.
- **★ 제목·소제목 = 간결한 선언형 명사구**(결론·내용을 *말하는* 명사구). 두 유형 금지 → (a) **질문형**('어떤 기회를 보았는가'·'무엇에 투자했나')·부정형·'X 현황/개요'류 토픽형, (b) **완결 문장형·서술 흐름**('규제 3단계 해소로 미가동에서 가동으로'처럼 '~로 ~으로'·'~해 ~됨' 주어+서술어로 읽히는 제목 — *제목은 문장이 아님*). ❌ '어떤 기회를 보았는가' / '규제 해소로 가동으로' → ✅ '진출 의도와 세부 영역' / '규제 제약 3단계 해소'. 본문 명사형뿐 아니라 *제목 형태*도 매 빌드 점검(audit declarative-headings lens). cf. [[declarative-section-headings]].
- **AI틱·비전문 워딩 제거**: '역설', '앞으로도 별볼일 없다', '파격', '폭발', '윈드폴', 드라마틱·과장 표현. 객관·선언형으로.
- **★ 격식 어휘 — 구어·비유·은어·문어투를 정식 실무어로(전수 스윕, 대표어만 고치고 끝내지 말 것).** '직관적이되 비즈니스 프로페셔널'은 쉬운 말이되 어휘는 정식 용어라는 뜻. 대표 치환 사전(같은 부류의 다른 표현도 함께 훑을 것): **①동사·서술** 열다→개설 · 두다→보유 · (자금)굴리다→운용 · 삼다→활용 · (수요)몰리다→집중 · 넘어오다→전환 · (사례)나오다→발생·이뤄지다 · 묶다/묶음→결합 · 얹히다→더해지다 · 넓히다→확대 · 만들다→마련·도입 · 쓰이다→활용 · 보여주다→제시 · **②부사·연결** 한꺼번에→일괄 · 곧바로→즉시 · 이제 막→이제 · ~라서/~이라(구어 인과)→~이므로·~이어서 · **③비유·은어 명사** 문턱→진입 장벽 · 발판→기반 · 먹거리→수익원 · 대못→핵심 제약 · 死제도→미가동 · 물량→거래량·거래 규모 · 양방향/강자끼리→상호·선도사 간 · 마중물·빡셈·조이다·서빙·핏 · **④구문** '아무 ~나 ~한 게 아니라'→'임의로 ~한 것이 아니라' · '~게 아니라'→'~것이 아니라'. 지목된 한두 개만 고치지 말고 *매 빌드 전 문서 전체를 이 부류로 훑는다*(비동기 audit `consulting-register` lens가 사전 스캔). **★ 스윕은 원형뿐 아니라 활용형까지 훑고**(접다: 접고/접기/접었, 닫다: 닫았다/닫는; 사전에 '접다=(사업)종료/철수', '닫다=폐쇄' 추가), **빌드 스크립트가 아니라 생성된 docx 실물 텍스트를 python-docx로 추출해 grep**한다(빌드 스크립트만 원형을 훑으면 활용형이 새어 감사에서 반복 적발됨. 실사례: 클라 docx register 교정을 빌드 스크립트에서만 해 '접기'·'닫았다'가 감사 2회 소모). cf. [[avoid-translationese-korean]].
- **★ 엠대시(—) 리드·절잇기 금지(번역체).** '리드 — 설명'처럼 엠대시로 절을 잇는 리드는 번역투로 읽힘 → **콜론(':')** 이나 완결 문장으로. 본문 절잇기도 엠대시 대신 문장을 끊거나 쉼표·괄호로. cf. [[avoid-translationese-korean]] 엠대시 절잇기 스윕.
- **가운뎃점(·) 띄어쓰기**: 여러 항목을 가운뎃점으로 *공백 없이* 연속 나열(`A·B·C`)하면 뭉쳐 읽힘 → **공백 둔 ` · ` 또는 쉼표**로(`A · B · C` / `A, B, C`; 긴 나열은 쉼표 권장). 표·헤더·본문 모두.
- 메타 코멘트("쉽게 말하면", "주목할 점은", 독자 직접 호명) 금지. research-organizer SKILL §10-bis의 A~J 스윕을 동일 적용.
- **★ 불릿·문단 리드는 완결 서술 — 노트식·정체불명 라벨 금지(반복 지적).** (a) 한두 단어+콜론의 작업노트식 라벨('언제:'·'왜:'·'어떻게:'·'요약:'·'결론:')과 (b) *정체불명·모호* 라벨('일부 세부:'·'기타:'·'관련 사항:'처럼 라벨만 읽어선 내용이 안 잡히는 것)을 달지 말 것 → **굵은 명사구 헤드라인**('철수 배경.'·'로스터의 시간 경계.')이나 **완결 문장**('검증 결과, 반납은 5개사임.')으로, *내용이 곧장 읽히는* 리드. ※ 내용이 분명한 서술형 명사구 리드('직접 계좌개설 구성:'·'제휴별 고객 기반:')는 허용. 비동기 audit `no-note-label-bullet` lens가 적발.
- **★ 요청자·요청 지칭 메타 워딩 금지(반복 지적)** — '컨설턴트(가 요청/언급)'·'의뢰'·'고객 요청'·'질문 흐름'·'추가 문항' 등 *누가/왜 이 산출물을 요청했는지*를 가리키는 표현을 본문·제목·메타라인에 넣지 말 것. 산출물엔 *사실·분석만* 남기고 요청 맥락은 비노출. 예: ❌ '컨설턴트가 언급한 해외 금융그룹 E MOU' → ✅ ''2004~2005 해외 금융그룹 E MOU'설'; ❌ '(추가 문항 ①) …' → ✅ 항목명 없이 바로 사실 진술; ❌ '컨설턴트 질문 흐름 정렬' → ✅ '진출의도→투자→…→철수 순'. cf. [[consulting-register-always]].

### 3) 사실/분석 분리 + [분석] 레퍼런스 grounding (가이드 §8 / 방법론 B-6)
- **사실**(출처 derive)과 **[분석]**(본 보고서 해석)을 명확히 분리.
- **★ 모든 `[분석]`은 레퍼런스 grounding 필수 — 없으면 삭제.** 각 [분석]은 *이 산출물의 인용 출처/데이터에서 도출*되거나 comparable·proxy + 출처를 동반해야 함(밸류풀 v28식 "값+도출근거+출처"). 어느 출처도 뒷받침하지 않는 **순수 LLM 일반지식 분석(뇌피셜) 금지** → 근거를 못 대면 *삭제* 또는 〈한계〉로 강등. 합성 framing(예 "두 축"·"라인별 1:1 대응")도 *어느 출처의 어느 진술에서 도출됐는지* 명시(refs 부착). cf. [[analysis-must-be-reference-grounded]].
- **이점/주장 렌즈 우선**: 근거(수치·인용)를 넣기 전 *"이건 어떤 이점·주장의 근거인가"*를 먼저 규정하고 관점별로 묶음(예 기대효과 = 운영효율·시너지·전략유연성 관점). 근거만 나열 금지.
- Bear/Bull도 사실과 [분석]으로 구분 기재.
- '비약적(비선형) 성장' 섹션은 외생 충격으로 급격 확대 가능한 트리거만, 점진적 동력은 Bull로(E-10). 두 섹션 중복 금지.

### 3-bis) 해석·시사점·비교 동반 + 용어 인라인 (독자가 문서만 읽어도 이해)
- **팩트·표 나열로 끝내지 말 것 — 해석은 *왜 그렇게 됐는가(근본 원인·메커니즘)*까지.** 각 항목의 *의미·시사점(so-what)*·*항목 간 비교 해석*을 동반하되, **현상 재진술('X 부담이 없다'·'A라서 A')·동어반복(1+1=2 류)은 인사이트가 아님** — "한 단계 더 *왜?*"를 자문해 근본 원인까지 내려갈 것. 기호·숫자를 가려도 '무엇을·왜'가 읽혀야 함(안 읽히면 데이터 덤프 = 실패). *(실사례: '충당 부담이 없어 이익이 높다'[현상 재진술] → '경쟁행은 *부실 은행을 인수*해 정리비용을 떠안았으나 당행은 깨끗한 자체 장부라 그 비용이 없다'[근본 원인]까지가 인사이트.)*
- **★ 리드 앵커 — 각 문단·불릿은 '무엇에 관한 말인지'를 밝히는 짧은 리드로 시작한다.** 첫 두세 어절에서 주제·결론을 못박고(괄호 태그 `(경쟁)`·굵은 리드어·리드 명사구 등) 근거로 넘어갈 것. 맥락 없이 사실·수치부터 던지면 독자가 '이게 무슨 얘기인지'부터 헤맨다 → **각 항목 = 리드(무엇/결론) → 근거(수치·인용) → (그래서) 시사점 3단**.
- **★ 논리를 *명시적으로* 이어라 — 점 잇기를 독자에게 떠넘기지 말 것.** 'A라서 B, B라서 C'의 인과·근거 연결을 문장으로 드러낸다(A→B→C). *결론만 던지고 근거 생략*하거나 *사실만 나열하고 연결 생략*하면 읽어도 뜻이 안 잡힌다 — 왜 그 결론인지·앞뒤가 어떻게 이어지는지를 매번 명시.
- **★ 한 문장 = 한 주장.** 여러 주장을 엠대시·쉼표로 한 문장에 뭉친 만연체 금지(무슨 말인지 흐려짐) → 짧게 끊어 하나씩. cf. [[avoid-translationese-korean]] 엠대시 절잇기 스윕.
- **★ 판정·헤드라인은 양면을 한 문장에.** 결론 문장은 기회와 제약(강점과 한계)을 함께 담아 한쪽만 말해 생기는 오해를 막는다(❌'매력적 시장' → ✅'매력은 있으나 ~로 수익성은 제한적').
- **★ Executive Summary = *결론·핵심 수치·so-what*만(가이드 §5-A④).** 익썸에 **정크 문장 금지** — 교차참조('…는 §X/1.1절 참조')·용어/개념 정의·검증/절차 캐비엇·동어반복은 빼서 *본문으로*. **리트머스: 익썸 각 문장이 '결론/판단/핵심 수치'인가** — 정의·참조·과정 설명이면 정크. *(실사례: 익썸의 'KBMI는 …분류이며 이유는 1.1절 참조'는 정의+교차참조 정크 → 삭제하고 등급·수치 결론만.)*
- **★ 비교 대상은 *항구적 정체성(주력 사업·기능·고객)* 중심으로 기술 — *일시적 상태*로 규정하지 말 것.** 비교표·프로필에서 각 대상(은행·회사 등)을 '무엇을 *하는가*(주력 사업·세그먼트)'로 적고, 일시적 상태(정상화 국면·실적 등락·당기 손익)는 부차적으로만 첨부. *(실사례: 경쟁행을 '정상화 국면'[상태]이 아니라 'UMKM·리테일 중심'[주력 사업]으로 기술.)*
- **용어는 *그 문장·표 안에서* 풀이** — 별도 용어사전에만 모아 독자가 알아서 찾아 이해하게 떠넘기지 말 것. 약어·전문어는 괄호로 1차 풀이(예: 'DTSP(해외 고객 전용 영업 차단)'·'VATP(가상자산 거래소 면허)'). 용어사전은 보조이며 둘 때도 문서 뒤쪽.
- **★ 자명한 기본 설명·불필요한 반복 금지.** (a) 정의만 읽어도 자명한 부연은 삭제(예: 방향을 '외국인→한국주식'으로 정의해 놓고 다시 '기존 거래와 정반대'라고 되풀이 = 군더더기). (b) 같은 jargon·개념어를 여러 절에 남발하지 말 것(디테일 과잉 — 한 번 정의했으면 반복 설명 불요). (c) **섹션 간 제목·내용 중복 금지** — 두 섹션 제목에 같은 말('시사점' 등)이 겹치면 내용이 실제로 겹치는지 확인하고, 겹치면 한 섹션으로 합치거나 논지를 갈라라(예: 한 섹션은 수익 메커니즘, 다른 섹션은 전략 시사점). 리트머스: 각 문장이 *비자명한 정보·판단*을 더하는가. 비동기 audit `no-obvious-or-redundant` lens가 적발.

### 4) 단위·실적/전망 (방법론 E-4·E-5)
- 통화·대규모 수치는 영어식 `$13B`/`$1.4T`(한글 "1396십억" 금지). 1인당 GDP 등 자릿수 검증.
- 성장률·실적 표는 **실적/추정/전망** 구분 표기(아직 오지 않은 연도를 실적처럼 쓰지 않음).

### 5) Tier 라벨 — 산출물에서 제거 (가이드 §8 / 방법론 E-9)
- **작업 마스터(.md)**: Tier 라벨 유지. **클라이언트 docx**: Tier 등 메타 라벨 제거. 출처 섹션 헤더에 "(Tier 0~1)" 같은 등급 표기 금지(`src_section`은 이미 등급 미표기).
- **★ `[분석]`·`[사실]` 등 대괄호 태그도 클라 docx에선 제거(반복 지적).** 사실/[분석] 분리(§3)는 *마스터 .md의 관행*이며, 클라이언트 docx엔 대괄호 태그를 *글자 그대로* 남기지 말 것 — 판단은 완결 서술문('~로 판단됨' · '결국 ~의 문제임')으로 문서의 목소리에 녹이고 근거 `[R#]` 링크만 유지. *실사례: 클라 docx 불릿에 '[분석] …'을 리터럴 노출 → '장난이냐' 지적.* 비동기 audit `no-worknote-meta-tag` lens가 적발.
- 라벨↔출처 1:1 매핑, 결번 0(R8 누락 같은 갭 점검).

### 6) 버전·diff 보존 (가이드 §9·§10 / 방법론 E-7)
- **★ 저장은 `D.save_versioned(doc, folder, stem[, major=True])`로 — 고정 파일명 `doc.save()` 금지.** 재빌드마다 폴더를 스캔해 새 `vN_M`을 자동 발행(기존 파일 있으면 예외=clobber-proof)하고 직전 minor를 `이전버전\`으로 자동 이관. 사람은 major/minor만 판단(기본 minor). 수동 파일명 지정·이동이 사라져 **덮어쓰기가 구조적으로 불가**(반복 덮어쓰기 실수 근본 차단). cf. `scripts/docx_helpers.py`의 `next_version_path`/`archive_superseded`.
- 기존 산출물 덮어쓰기 **절대 금지** → *변경이 있으면(워딩 한 줄이라도) 잠김 여부와 무관하게 무조건* 새 버전 + CHANGELOG. 표기 **`vN_M`**(N=앞=주요[구조·핵심수치·결론 변경], M=뒤=경미[워딩·재빌드]): 경미 수정 M++, 주요 수정만 N++(M=0). **★ N은 *주요 변경이 생긴 즉시* 올리고(전달/사인오프 시점까지 minor로 끌지 말 것), N++ 후엔 다듬어 어느 `vN_M`에서 보고·전달한다(`vN_0` 자체를 보고본으로 쓰지 않음 — 시작점일 뿐).** **★ 이관 규칙(자주 틀림): ① M++(경미) 시에만 직전 minor본을 `이전버전\`으로 이관 → 메인엔 *현 major의 최신 minor 1개*만. ② N++(주요) 시에는 직전 major를 메인에 *그대로 보존*(이전버전 이관 X) — 주요 버전은 메인에 누적.** 예: `v1_0→v1_1`이면 v1_0 이관 / `v1_2→v2_0`이면 v1_2는 메인 유지. **③ 주요 버전(N)이 메인에 5개를 넘게 누적되면 가장 오래된 major부터 `이전버전\`으로 이관**(메인엔 최근 ~5 major 유지). **모든 산출물(.md·docx 등)에 동일 규칙 일관 적용**(한쪽만 다르게 금지 — 과거 .md는 다 남기고 docx만 이관해 불일치·flat번호로 major/minor 구분 자체가 사라진 적 있음). 구버전 보존(삭제 아님). 빠른 반복 중엔 `_working.docx`로 작업 후 합의 시 `vN_M` 승격 허용. cf. [[deliverable-versioning]].
- **★ 잠김 여부와 무관하게 *모든 변경은 새 `vN_M` 파일*로 발행(덮어쓰기 절대 금지). 파일 잠김(PermissionError)은 '새 버전을 만드는 *조건*'이 아니라 그저 또 하나의 새-버전 사유일 뿐 — 잠겼다고 빌드를 멈추지 말 것.** (오적용 사례: 잠김이 아니라며 직전 버전을 in-place 덮어씀 → 금지.)
- 사용자가 docx를 수동 편집했을 수 있으면, 재빌드 전 **기존 파일 텍스트 추출 → diff**로 수동 편집을 식별해 보존(헤더 축약 등 미세 편집도 누락 금지).
- 수정 시 **ripple grep**: 한 수치/표현을 바꾸면 문서 전체에서 같은 값·연결 서술을 grep해 동반 수정(가이드 §9).
