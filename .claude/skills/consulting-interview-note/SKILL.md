# 컨설팅 펌 Interview Note Skill

> 공개본 안내: 서식 가이드(`style_guide.md`)와 예시 회의록(`references/reference_example.docx`)은 실제 회의 기록을 바탕으로 해 이 저장소에 포함하지 않았다. 아래 절차에서 두 파일을 읽는 단계는 비공개 자료를 전제로 한다.

> ### ▶ 단계 게이트 (빠른 바닥은 인라인, 빡빡한 양식·워딩 검수는 비동기 gate-audit)
> hook 차단 환경의 강제 레버. 헬퍼 `SG` = `python3 <REPO>/.claude/skills/_stepgate/stepgate.py`.
> **★ 동시 작업 격리** — 이 워크플로의 *모든* SG 호출(form·judge·resolve)에 **같은 `dir=<과제폴더 절대경로>`**를 붙인다(다른 과제=다른 폴더→자동 격리, 같은 폴더 다중 산출물은 `deliverable=`로 구분). 누락 시 form↔judge 키가 갈려 오작동.
> **① 생성 직후(바닥)**: `SG form consulting-interview-note deliver dir=<과제폴더>` → 산출 docx·입력 확인하고 **정직히** 답(합격 기준 비공개·**표현이 회차마다 뒤집히니 지난 답을 재사용하지 말고 이번 문구를 그대로 읽고 답할 것**) → `SG judge consulting-interview-note deliver <id>=<값> … deliverable=<docx 절대경로> dir=<과제폴더>`. **GATE PASS**면 바닥 통과 → FIRE 블록으로 **백그라운드 감사 에이전트(general-purpose) 발사·즉시 다음 작업**.
> **② 제시 직전(해소)**: `SG resolve consulting-interview-note deliverable=<docx 절대경로> dir=<과제폴더>` → **RESOLVE PASS 아니면 제시/‘done’ 금지**(HOLD=동기 드레인·FAIL=수정·재감사).
> 체크포인트: **deliver**(사람 라벨 STT 입력·Step1 구조 확인 후 생성) → 비동기 lens 감사 → resolve. 봉인 루브릭(rubrics/) 직접 열람 금지(감사됨). 상세: `skill-maintainer` 〈단계 게이트 프로토콜〉.
> `<REPO>` = 이 저장소를 클론한 **절대경로**(문서상 표기). `dir=`·`deliverable=`은 절대경로여야 하므로 호출할 때 실제 경로로 치환한다.

클로바노트 STT TXT → 컨설팅 펌 표준 양식 미팅록(.docx) 변환 스킬입니다.
참조 미팅록(`references/reference_example.docx`)의 구조·문체를 정밀하게 복제합니다.

## 0. 목표 산출물 — 세 강점의 동시 충족 (먼저 읽기)

좋은 미팅록은 아래 **세 품질을 첫 산출물에 한꺼번에** 갖춰야 함. 어느 하나를 나중에 보완하는 방식이 아니라, 초안부터 셋을 동시에 겨냥할 것.

| 품질 | 핵심 | 수행 내용 | 상세 |
|---|---|---|---|
| **① 구조 충실** (미팅 흐름 그대로) | 덱·프레임 기반 미팅이면 그 그룹·번호 체계(#1~#N)를 본문 구조로 사용 / 다자 회의는 발화자별(`본부장 view`·`팀장 challenge`·`컨설팅 펌 정리`) 분리 / 구체 디테일(회사명·딜 밸류·거점·인물 이력) 보존 / 후속은 **Action Items 표**(Item·Owner·비고) | §4.2, §4.1, §8 |
| **② 정합성** (사실이 맞음) | 고유명사·귀속·수치를 **웹 검색으로 검증**해 본문에 확정(STT 오인식 교정) / 표준 컨설팅 펌 포맷(📌 Exec Summary 본문정렬·🔑 용어풀이·★ 핵심 섹션) 완비 | §9(style_guide), §4.1, §4.3 |
| **③ 정제** (녹취록 아닌 정돈된 회의록) | 명제 우선(명사형) / 시그니처 인용 섹션당 1~2개 / 트랜스크립트 텍스처(진행 괄호·구어 단편·run-on) 제거 | §11(style_guide), §1.4 |

**한 줄 요약**: "구조는 미팅 흐름 그대로 충실하게, 사실은 검증으로 맞게, 표현은 정돈된 명제로." 이 셋이 **동시에** 안 되면 미완성.

## 1. 입력 명세

### 1.1 필수 입력
- **STT TXT 파일 경로** — 클로바노트에서 export, 화자 라벨이 사람에 의해 입력 완료된 상태
- **메타데이터**:
  - `일시`: 예) `2026.06.01(월) 오후 2시`
  - `참석자`: 직함·소속 포함 전체 리스트, **고객사 인원 먼저 → 컨설팅 펌 인원 뒤로** 나열(고객사 내부는 인터뷰이→배석 순). **이름·직함·소속까지만 표기하고, 역할·참여형태 부연(예: `(도입부 인사)`·`(진행)`·`(배석)`·`(인터뷰이)`)은 참석자 표기에 넣지 않음** — 그런 맥락은 필요하면 미팅 배경 섹션 본문에서 서술. 예) `인터뷰이 A PE신기술투자부 부서장, 인터뷰이 B 전략기획부 팀장, 인터뷰이 C 이사(컨설팅 펌), 인터뷰이 D 컨설턴트(컨설팅 펌)`
  - `프로젝트 맥락` (선택): 인터뷰가 속한 프로젝트의 한 줄 배경. 미팅 배경 섹션 작성에 활용

### 1.2 메타데이터 미제공 시
사용자에게 위 항목을 **명시적으로 질문**한 후 진행. 추측 금지.

### 1.3 STT 본문 포맷 (둘 다 지원)
```
인터뷰이 A 이사: 발화 내용...
인터뷰이 B 팀장: 발화 내용...
```
또는
```
[인터뷰이 A 이사] 발화 내용...
[인터뷰이 B 팀장] 발화 내용...
```

### 1.4 발화자 라벨 정규화 — 컨설턴트 입력 불완전성 대응
컨설턴트가 클로바노트에서 라벨링했더라도, **표기 흔들림·오타·직함 누락**이 발생할 수 있음. STT 파싱 후 **반드시** 다음 절차를 거침:

1. **고유 발화자 목록 추출**: TXT에서 발견된 모든 라벨을 dedup해 목록 작성
2. **메타데이터 참석자 명단과 매칭**: 각 라벨이 참석자 명단의 누구와 일치하는지 매핑
   - 예) `인터뷰이 A 이사`, `박이사`, `인터뷰이 A`, `인터뷰이 A부서장` → 모두 `인터뷰이 A PE신기술투자부 부서장`에 매핑
3. **매핑 불확실 항목**: 참석자 명단과 일치 안 되는 라벨이 있으면 **초안 단계의 `⚠️ 확인 필요 항목`에 명시**하고 사용자 확인 요청
   - 예) "라벨 `김재영`은 참석자 명단에 없음 — `인터뷰이 B 팀장`의 오타로 추정. 확인 부탁드림"
4. **압축형 변환**: 최종적으로 본문에서 `박 이사`, `김 팀장` 식 압축 적용
5. **참석자 명단에 없는 라벨이 짧게 등장**(예: 진행자 멘트, 비등록 참석자)할 경우: 해당 발화를 미팅록에서 제외하거나, `(타인)` 등의 마커로 처리하는지 사용자 의견 확인
6. **동일 세션 복수 소스 크로스체크**: 같은 녹취가 여러 파일로 제공될 수 있음(예: 실명 라벨 STT + `Attendees 1~4` 익명 docx). 이때 **타임스탬프·문구 일치 여부를 확인**해 동일 녹취임을 검증하고, 익명 라벨↔실명을 매핑(`Attendees 1`=인터뷰이 E 파트너 …). 내용이 충돌하면 사용자에게 우선 소스를 확인

## 2. 워크플로우 — 2단계 필수

### Step 1. 구조 초안 마크다운 제시
TXT를 분석한 후, **docx 생성 전에 반드시** 아래 형식의 마크다운 초안을 사용자에게 보여주고 확인을 받습니다.

```markdown
# 초안: <인터뷰이>_미팅록

## 📌 Executive Summary
- (3~5문단 초안 — 인터뷰이의 메인 주장 → 부주장 → 결정적 인사이트 순)

## 섹션 헤드라인 목록
1. <섹션 제목 — 부연>
   - 핵심 메시지 1
   - 핵심 메시지 2
2. ...

## 🎯 시사점 / 후속 (후보)
- ...

## 🔑 용어 풀이 (후보)
- 2차 도매: ...

## ⚠️ STT 오인식 의심 / 확인 필요 항목
- "캔턴 네트워크" → 정확한 명칭/철자 확인 필요
- 수치 "5조 원" → 발음상 "50조 원" 가능성, 원문 확인 필요
```

**사용자에게 묻기**: "위 구조대로 docx 생성할까요? 수정/추가/삭제할 항목이 있으면 알려주세요."

### Step 2. 사용자 확인 후 docx 생성
사용자 승인(또는 수정사항 반영) 후 `scripts/generate_docx.py`를 호출해 워드 파일을 생성합니다.

**생성 전 셀프 체크리스트** (하나라도 미충족 시 JSON 보강 후 생성):
- [ ] **구조 적합(덱·발화자)**: 미팅이 컨설팅 펌 덱·프레임 기반이면 그 그룹·번호 체계(#1~#N)를 따랐는가 / 다자 회의면 발화자별(`본부장 view`·`김 팀장 challenge`·`컨설팅 펌 정리`)로 분리됐는가 (`§4.2`)
- [ ] **Exec Summary ↔ 본문 정렬**: Executive Summary가 **본문 섹션 내용을 대표하는 요약**인지 확인. 보고 방식·진행·메타 코멘트 위주로 채워졌으면 본문(섹션) 핵심 메시지 요약으로 교체
- [ ] **구어체 정제**: 종결뿐 아니라 문장 중간의 캐주얼 동사·평가어("건 별로", "집어주다", "끼지 말고", "낫지", "말이 되는지", "어정쩡하게", "그나마", "제대로", "잘하는", "터지다", "태우다", "드라이브" 등)를 격식 워딩으로 교체 (`style_guide §1.4`). **구어 표현은 인터뷰이 직접 인용("…") 안에서만 허용** — 내 해석·서술에 새어나오면 안 됨(구어가 보이면 "화자 인용인가, 내 서술인가" 먼저 판별)
- [ ] **정제 수준(raw 텍스처 제거)**: STT·1차 정리본을 거의 그대로 옮기지 않았는가 — 각 bullet이 **명제(명사형)로 시작**하고, **시그니처 인용은 섹션당 1~2개 이하**(풀어 쓰면 의미가 손상되는 대목에만, 남발 금지)이며, 진행·메타 괄호·구어 단편·run-on이 남아 있지 않은지 (`style_guide §11`)
- [ ] **볼드 밀도**: 각 번호 섹션(배경 섹션 제외)에 시그니처 명제 **볼드 1개 이상**. 볼드가 Executive Summary에만 있으면 미달 — `**…**`를 본문 핵심 명제에 부여 (`style_guide §3.1`: 섹션당 1~2개)
- [ ] **★ 핵심 섹션**: 미팅당 0~1개 핵심 섹션 제목에 ` ★`
- [ ] **Sub-bullet**: 비교·진화·열거(3건 이상 동질 항목)는 `level:1` 하위 bullet로 분해 (한 bullet에 run-on 금지)
- [ ] **표 변환**: 명시적 A vs B / 3개 이상 동질 비교는 표로 (`§5` 기준)
- [ ] **🎯 라벨**: 미팅 성격에 맞게 `implications_title` 선택 (현황 청취 → 시사점/후속, 실행 합의 → 액션 아이템/일정)

## 3. 문체 규칙 — 절대 준수

상세 규칙은 `style_guide.md` 참조. 핵심:

1. **종결: 명사형** — `~함 / ~음 / ~임 / ~중 / ~안` (예: "동의함", "추진 중", "필요한 사안임"). 합쇼체(~합니다), 해요체(~해요) **금지**.
2. **발언자 귀속**: `박 이사:`, `김 팀장:` 식의 압축 표기. 풀네임은 헤더(참석자)에만 1회 등장.
3. **수치·인명·기업명**: STT 원문 보존. 오인식 의심 시 초안 단계에서 `⚠️` 마커로 사용자에게 확인 요청. **추측·보완 금지**.
4. **볼드**: 섹션당 핵심 명제 1~2개에만 `**굵게**`. 남용 금지.
5. **시그니처 인용 — 절제**: 인터뷰이의 특징적 표현은 `**"…"**`로 보존하되, **풀어 쓰면 의미가 손상되는 핵심 대목에만**(문서 전체로 손에 꼽을 정도, 섹션당 1~2개). 격식 명제로 동일 의미가 전달되면 인용하지 말고 풀어 쓸 것. **구어체 표현은 인터뷰이 직접 인용 안에서만 원문 유지** — 내 해석·분석 서술은 격식어로 전환(녹취록 화자의 구어가 회의록 서술로 새어나오면 안 됨). cf. `style_guide §1.4·§11.2`
6. **표 변환**: 본문에 명시적 비교 구조(A vs B 벤치마킹, 3개 이상 동질 항목)가 있을 때만 표로 변환.
7. **bullet 시작**: bullet은 명사구 또는 짧은 문장으로 시작, 끝은 명사형 종결.

## 4. 출력 구조 — 참조 미팅록 정밀 복제

### 4.1 고정 섹션 순서
0. **(선택) 미팅 제목 구분선** — `< 해외주식파생부 미팅 w/ 인터뷰이 F 부서장 >` (bold). 멀티미팅 마스터 문서일 때만. `meta.meeting_title`로 지정 → 4.4 참조
1. **헤더** (일시 / 참석자) — `일시:`/`참석:` **라벨만 bold**, 값은 plain (참조 미팅록 동일). **참석자는 고객사 인원 먼저(인터뷰이→배석) → 컨설팅 펌 인원 뒤로**, 한 단락에 콤마로 나열(헬퍼가 `(컨설팅 펌)` 태그를 뒤로 stable 정렬 + 한 줄 출력 → 인원을 별도 줄로 쪼개지 않음; 과거 80자 chunking이 마지막 참석자를 단독 줄로 떨어뜨리던 버그 제거)
2. **📌 Executive Summary** — bold 헤더 + 2~4문단 본문 (4.3 참조)
3. **번호 섹션 1~N** — `1. 제목 — 부연` 형태. 각 섹션 본문은 bullet 위주
4. **🎯 시사점 / 후속** — 2~3 bullet. **헤더 라벨 가변**: 미팅 성격에 따라 `🎯 액션 아이템 / 일정`, `🎯 컨설팅 펌 액션 아이템` 등으로 교체 (`implications_title`). **후속 액션이 구체적(담당·기한 존재)이면 prose bullet 대신 Action Items 표(Item·Owner·비고)로** — 워킹 미팅의 표준(마지막 번호 섹션에 table 객체로 배치)
5. **🔑 용어 풀이** — 본문에 등장한 약어·전문용어만 (일반 비즈니스 용어 제외)

### 4.2 섹션 헤더 분류 기준
- **번호 섹션 (1~N)**: 인터뷰의 주제 흐름. 보통 6~9개 섹션
- 각 섹션은 인터뷰이가 시간을 들여 다룬 **하나의 토픽 클러스터**
- **프레임워크·덱 기반 구조 (중요)**: 미팅이 컨설팅 펌가 제시한 프레임워크·덱(예: 14개 사업모델, 밸류체인 맵)을 따라 인터뷰이가 **항목별로 반응**하는 형태면, 임의의 평행 주제를 새로 만들지 말고 **그 프레임의 그룹·번호 체계(#1~#N)를 본문 구조로 그대로 사용**(컨설턴트가 덱과 1:1 대조·추적 가능해야 함). 토픽 클러스터 재구성은 덱 없이 자유 청취한 인터뷰에만 적용
- **다자 회의의 발화자별 구조**: 인터뷰이 1인이 아니라 여러 참석자가 **각자 다른 view·challenge**를 낸 회의면, 블록을 **발화자별로 명시 분리**(`본부장 view`, `김 팀장 challenge`, `컨설팅 펌 정리` 등). 누가 무슨 말을 했는지 섞이면 안 됨
- **제목 컨벤션** (참조 미팅록 패턴):
  - `1. 제목 — 부연` (부연은 em dash로 연결)
  - **핵심 섹션 1개**엔 제목 끝에 ` ★` 부착 (예: `3. 글로벌 전략의 핵심 고민 — "코너링 전략" ★`). 남용 금지, 미팅당 0~1개
  - 특정 발언자 귀속·상태는 괄호 부연 (예: `7. 글로벌 자산 비중 가이드라인 (김 팀장 답변)`)
- **Sub-bullet 활용**: 비교·진화·열거(예: `(기존)/(현재 ①)/(현재 ② 핵심)`)는 `level:1` 하위 bullet로 들여쓰기 1단계. 실제 미팅록이 빈번히 사용 (3단계 이상 중첩 금지)

### 4.3 Executive Summary 작성 공식
표준 구조는 3~5문단이나, **인터뷰 분량에 따라 유연하게 조정**:
- **1문단**: 인터뷰이의 메인 주장 1줄로 압축 + 그 주장의 핵심 근거
- **2~3문단**: 부주장·부논점 (메인과 독립적인 추가 인사이트)
- **마지막 문단**: 인터뷰 말미의 감정적·전략적 메시지 (위기감, 기대, 비전 등)

**분량 예외 규칙**:
- 인터뷰 본문이 **단일 주제 또는 짧을 때**(STT 약 30분 이하 또는 토픽 1~2개): **1~2문단으로 압축** 허용. 메인 주장 + (있다면) 결정적 인사이트만 담음.
- **분량 맞추기를 위한 내용 중복·인위적 늘리기 절대 금지**. 압축이 자연스러우면 압축이 우선.

### 4.4 멀티미팅 마스터 문서 (선택)
실제 산출물은 여러 인터뷰를 **한 파일에 누적**하는 경우가 있음(예: 한 주간 진행한 4개 부서 미팅을 묶음).
- **최상단 표지**: `컨설팅 펌 – 고객사 A(증권사)` + 미팅 목록(TOC)을 bullet로 나열. 예) `전략기획본부 미팅 w/ 인터뷰이 G 본부장 (5/27, 수)`
- **각 인터뷰 시작**: `meta.meeting_title`을 지정하면 `< … 미팅 w/ … >` (bold) 구분선이 일시/참석 위에 출력됨
- 단건 인터뷰만 정리할 때는 `meeting_title`을 생략하면 됨 (기존 동작과 동일)
- 마스터 문서 누적은 generate_docx 단건 실행만으로는 불가 → 사용자가 기존 마스터에 붙일지, 단건으로 낼지 **먼저 확인**

### 4.5 변형: 내부용 · 사용자 지정 구조
표준 구조(번호 섹션 + 용어풀이)는 고객사 공유용 기준. 미팅 성격·요청에 따라 다음 변형을 적용:
- **내부용(고객사 비공유)**: `🔑 용어 풀이`를 **생략**(`glossary` 미포함). 문체(명사형·격식)는 동일하게 유지. 사용자가 "내부용"이라 명시하면 용어풀이 자동 제외
- **사용자 지정 분류 버킷**: 사용자가 특정 분류를 지정하면(예: `<글로벌 Legacy>`/`<Web 3>`/`<24시간 운영체계>`) 번호 섹션 대신 그 카테고리를 섹션 제목으로 사용. generate_docx에서 `number`를 생략하고 `title`에 `<…>` 표기를 그대로 넣으면 번호 없이 출력됨
- **특정 발화자 코멘트 기반**: 한 명(예: 파트너·그룹장)의 코멘트 중심으로 정리하라는 요청 시, 그 발화자의 디렉션을 본문 주축으로 하고 타 발화자는 맥락·귀속(`인터뷰이 H:` 등)으로만 인용. Executive Summary도 그 발화자 메시지 기준으로 작성

## 5. docx 생성

`scripts/generate_docx.py`를 사용합니다.

```bash
python3 scripts/generate_docx.py \
  --output "/path/to/YYMMDD_<인터뷰이>_미팅록_v1.docx" \
  --json /tmp/interview_data.json
```

`--json` 입력 스키마는 `scripts/generate_docx.py` 상단 docstring 참조. 핵심 필드:
- `meta`: `date`, `attendees` (+ 선택 `meeting_title` — 멀티미팅 구분선)
- `executive_summary`: 문단 배열 (각 원소가 한 문단)
- `sections`: `[{number, title, body}]` — body는 bullet 배열, 또는 표(table) 객체. bullet은 `{type, text, level}` (level:1 = 하위 bullet)
- `implications_title`: 선택. 🎯 헤더 라벨 (기본 `🎯 시사점 / 후속`)
- `implications`: bullet 배열
- `glossary`: `[{term, definition}]`

본문 내 볼드/인용 강조는 마크다운 `**…**` 패턴으로 작성하면 헬퍼가 docx run으로 변환합니다.

### 5.1 발행 후 정리 (클린업) — 필수
JSON은 docx를 찍어내기 위한 **중간 산출물(build artifact)**일 뿐, 영구 보관물이 아님. docx 발행·검증이 끝나면 **JSON과 임시 스크립트를 삭제**해 산출 폴더를 깨끗이 유지한다.
- 산출 폴더에는 **버전별 `.docx` + 단일 `CHANGELOG_<인터뷰이>_미팅록.md`만** 남긴다(영구 기록은 CHANGELOG 하나로 일원화 — §6.1).
- JSON(`*_data_*.json`)·STT 추출용 임시 `*.py`는 검증 후 **삭제**(`$env:TEMP` 등 작업 폴더에 만들었다면 그대로 휘발). 삭제 전 대상 경로를 한 번 확인하고 `Remove-Item`.
- 세션 중 반복 수정(v2·v3 …)이 진행 중이면 JSON은 그 작업이 끝날 때까지 유지하고, **최종 산출물 확정 시점에 일괄 삭제**(작업 중간엔 재생성·diff에 활용).

## 6. 파일명 규칙

출력 파일명 기본 패턴:
```
YYMMDD_<인터뷰이 이름> <직책>님_미팅록_v1.docx
예) 260616_인터뷰이 I 부법인장님_미팅록_v1.docx
```

YYMMDD는 인터뷰 일자(메타데이터의 `일시`에서 추출). 인터뷰이가 여러 명이면 가장 시니어 1명 기준.

**파일명 직책·존칭 규칙 (파일명 한정)**: 파일명에는 **인터뷰이의 직책을 유지**하고, **이름(직책이 있으면 직책) 뒤에 "님"을 무조건 붙인다**. 직책이 명확하지 않거나 누락된 경우에도 최소 `<이름>님`으로 "님"을 반드시 부착(예: 직책 불명 → `260616_홍길동님_미팅록_v1.docx`). ※ 본문 발언자 귀속(`박 이사:`)·헤더 참석자 표기에는 "님"을 붙이지 않음 — "님" 부착은 **파일명에만** 적용(§3.2·§1.4 표기는 그대로 유지).

### 6.1 버전 관리 — 절대 준수
- **기존 산출물 덮어쓰기 금지**. 미팅록이 수정되면 **반드시 새 버전 파일**(`…_v2.docx`, `_v3.docx` …)로 발행
- **JSON 소스는 영구 보존하지 않음** — 빌드용 중간 산출물이므로 발행·검증 후 삭제(§5.1). 버전 이력은 **CHANGELOG 단일 파일로 일원화**(다른 산출물 스킬과 동일 컨벤션). 재생성이 필요하면 STT + CHANGELOG 변경 기록을 근거로 JSON을 재구성
- **CHANGELOG** 파일(`CHANGELOG_<인터뷰이>_미팅록.md`)이 **유일한 영구 기록** — 출력 폴더에 두고 버전별 변경 요지·최신본 표시를 갱신(어떤 버전이 무엇을 바꿨는지, 무엇이 최신본인지를 여기서만 추적)
- 최초 발행은 `_v1`. 단순 오타 수정도 새 버전으로 올림(버전 번호는 아끼지 않음)
- 초안 단계 반복(Step 1)은 버전이 아님 — **docx로 발행된 산출물**부터 버전 카운트

## 8. 절대 하지 말 것

- **단계 게이트(2단계)**: ① `SG judge consulting-interview-note deliver … deliverable=<docx> dir=<과제폴더>` → **GATE PASS**(사람 라벨 STT·구조 확인·화자 임의생성 아님) + 백그라운드 gate-audit 발사. ② 제시 직전 `SG resolve consulting-interview-note deliverable=<docx> dir=<과제폴더>` → **RESOLVE PASS**(form·judge·resolve 전부 같은 `dir=` — 동시작업 격리). RESOLVE PASS 아니면 제시/‘done’ 금지 · 봉인 루브릭 직접 열람 금지
- **추측 보완 금지**: STT에 없는 내용을 일반 비즈니스 상식으로 채우지 않음
- **합쇼체·해요체 금지**: 명사형 종결 일관성 유지
- **이중 인사말 금지**: "감사합니다", "수고하셨습니다" 등 인터뷰 진행 멘트는 미팅록에서 제거
- **자동 메일 본문 생성 금지**: 현재 스킬 범위는 워드 산출물만. 메일 본문은 컨설턴트가 별도 작성
- **화자 분리 임의 수정 금지**: 사람이 라벨링한 화자 정보를 임의로 수정하지 않음
- **과도한 추상화 금지**: 인터뷰이가 준 **구체 고유명사·수치(회사명·딜 밸류·라이선스/거점명·인물 이력)를 일반어로 뭉개지 말 것**. 예) '외부 발행 플랫폼'이 아니라 '핀테크 A·핀테크 B', '거래소 A holdout'은 '$15억 밸류 부담'까지 — 컨설턴트가 미팅록만으로 디테일을 복기할 수 있어야 함
