# Trade Feedback — 놓친 급등을 규칙 수정으로 되먹인다

> ### ▶ 3단 게이트 — 단계마다 통과한다
> 헬퍼 `SG` = `python3 <REPO>/.claude/skills/_stepgate/stepgate.py` (**표기일 뿐 — 셸 변수로 만들지 말고 매번 전체 경로**)
> ```
> collect → propose → apply
> ```
> 각 단계는 ① `SG form trade-feedback <cp> dir=<프로젝트폴더>` → ② 실물을 보고 **정직히** 답
> (합격 기준 비공개 · **표현이 회차마다 뒤집히니 지난 답 재사용 금지**) →
> ③ `SG judge trade-feedback <cp> <id>=<값> … week=<YYMMDD> deliverable=<그 단계 산출물 절대경로> dir=<프로젝트폴더>`.
> **GATE PASS 아니면 다음 단계로 넘어가지 않는다.** 시작 전 `SG clear trade-feedback dir=<프로젝트폴더>`.
> 게이트 루브릭 직접 열람 금지(열람은 감사된다).
> `<REPO>` = 이 저장소를 클론한 **절대경로**(문서상 표기). `dir=`·`deliverable=`은 절대경로여야 하므로 호출할 때 실제 경로로 치환한다.

**프로젝트폴더** = `<REPO>/ai-trading-bot` — 명령은 전부 여기서 부른다.
**주차(`week`)** = 이 피드백을 도는 토요일의 `YYMMDD`. 수동 호출이면 그날 날짜.

**왜 있는가 (2026-10-02 사용자)** — "매수하지 않았는데 엄청 오른 종목들이 있더라고 … 삼성전자 같은 메인 종목인데
그걸 캐치 못하는 게 말이 안 되는 것 같거든 … 안 산 혹은 못 산 이유랑 과거에 어떤 평가들을 했어야 했는지 스스로
피드백하고, 필요하면 스킬을 고치는 한이 있더라도 돈을 더 잘 벌 수 있는 방법을 끊임없이 연구해."
회고·아쉬움 감사·주간 리포트는 숫자를 냈지만 **규칙으로 돌아가는 길**이 없었다 — 규칙은 사용자가 지적할 때만 바뀌었다.
이 스킬이 그 길이다.

## 0. 원칙 — 여섯 가지를 어기면 피드백이 소음을 쫓는다

1. **근거가 틀렸을 때만 고친다.** 종목마다 판정은 셋 중 하나다 — `결함`(그때 손에 있던 재료로 다르게 했어야 했다) ·
   `맞은 판단`(막은 규칙이 실제 위험을 피했다) · `운`(그때 단서가 없었다). 결과만 보고 고치면 좋은 규칙을 나쁜 결과
   때문에 버린다. 원장(`feedback.py`)은 결함이 아닌 행의 규칙 변경을 **기계로 거부**한다.
2. **사후 지식으로 채점하지 않는다.** "언제 무엇을 평가했어야 했나"는 **고점 전 날짜의 우리 기록**(재료·노트·리서치·
   작업기록·시그널 — 수집의 평가 이력)에 있던 단서를 인용해야 한다. 고점 전에 단서가 하나도 없었으면 `운`이다 —
   단, **커버리지 결함**(시총 상위인데 유니버스·지도 밖이라 아예 안 봤다)은 단서 유무와 무관하게 `결함`이다.
3. **사례가 아니라 유형으로 고친다.** "그 종목을 다시 샀어야 했다"는 규칙이 아니다. "이익실현 다리가 체결되면 재진입
   조건을 같이 건다"가 규칙이다. 제안의 `cause`에 증거 종목의 이름·티커가 있으면 원장이 거부한다.
4. **되돌릴 수 있는 것만 자동으로 고친다.** 모든 적용에는 다음 주 검증 지표가 붙고, 나아지지 않으면 철회가 기본이다.
   권한 범위는 `config/feedback_policy.json`이 정한다 — **그 파일이 없으면 전부 승인 대기**(제안만, 적용 0).
   안전장치(손절·집중 공개선·실전 래치·자금 규칙)·숫자 상수(`safety`·`param`)는 정책이 있어도 승인 대기다.
5. **목적은 돈을 최대한 많이 버는 것이다 — 10%는 바닥(하한)이지 목표가 아니고 위로는 상한이 없다(2026-10-03 사용자).**
   규율 지표만 지키고 기회를 계속 놓치면 그것도 실패다(`trade-run` §0 "안 사는 것이 기본값이면 안 된다"). 수집 머리의
   계좌 30일 수익률 줄이 바닥 미달이면 §1 첫 줄에 그대로 옮긴다 — "목표 달성" 같은 표현은 쓰지 않는다. 반대로 새 규칙이 **다른 종목에서 손실을 냈을 경우**도 같이 본다 — 아래 2단의 반례 점검.

6. **손실·시나리오 오판은 논지가 등록 때 정한 시계로만 판정한다 — 가격 하락만으로 오판을 주지 않는다(2026-10-12 사용자:
   "너무 단기간만 보고 빡빡하게 하면 안 된다 — 일시적으로 안 좋은 건지 제대로 잘못 예상한 건지를 판단하라").** 판정은 셋이다.
   - **오판** — ⓐ 무효 조건(판정 다리 — 훼손·무효·반증)이 충족돼 집행됐다 ⓑ 논지 기한이 지났는데 손실이다 ⓒ 축 전망이 기한을
     넘겨 `miss`다 ⓓ 손절·추적 다리가 손실로 발화했다(논지가 말한 동인이 멀쩡하면 '동인 불일치', 꺾였으면 '방향').
   - **일시적** — 넷 다 아니다. 가격만 빠졌다. **관찰** — 근거가 엇갈린다(연쇄에 반증이 섞였는데 시점이 불분명 등).
     둘 다 `next_check`를 달아 다음 주로 이월한다 — 이월한 행을 이번 주 규칙 변경의 근거로 쓰지 않는다.
   - **오판이면 유형을 붙이고 고칠 자리로 보낸다**: 지연·가지 누락 → `stage3_map.md` 세 갈래 · 동인 → `theses_levels.md`
     `price_driver` · 충돌 → `conflicts_with` · 집중 → 요인(`driver`) '꺾이면' 행 · 크기 → `stage5_decide.md` 4-b ·
     방향 → 전망 확신도·반대 축. 고칠 때는 원칙 1~4가 그대로다(진입 전 단서 인용 · 유형 문장 · 반례 · 되돌릴 수 있는 것만 자동).
   - **빡빡함은 매주 스스로 잰다** — 지난주 '일시적'이 이번 주 손실로 닫혔으면 느슨, 지난주 '오판'이 고점을 다시 넘었으면
     빡빡. 그 비율이 `loss_verdict_flip_rate`(보정표 · §4)다.
   - 손익은 **순실현**으로 잰다 — 손실 난 매매만 더하지 않는다. *실사례(2026-10-12): 손으로 시킨 손실 분석이 손실 매매만 더해
     −58.4만 원이라 썼는데 순실현은 −16.7만 원이었고, '손실 묶음'에 실현 +5.7만 원 종목이 섞여 있었다.*

**무인(`auto`) 실행** — 질문하지 않는다. 권한 밖은 원장에 `confirm`으로 남기고 보고에 적는다. 도구 오류·조회 실패는
멈추지 말고 보고서 §6 한계에 적고 다음 단계로 간다.

## 1단 수집 — `collect`

```
python3 journal.py --weekly                       # 주간 리포트에 ④절(전망·아쉬움)이 없으면 먼저
python3 main_names.py --show                      # as_of가 90일을 넘었으면 --refresh(시총 상위 재측정)
python3 run_tests.py                              # 약 1분 — 테스트 완주 기록(멈춤·실패·건수 감소면 ★) · 수집 머리에 그 줄이 박힌다
python3 feedback.py collect --week <YYMMDD>       # 약 4분 — data/feedback/수집_<week>.md · .json
```

**테스트를 매주 끝까지 돌린다**(2026-10-11 사용자: "테스트가 멈추지 않도록 · 멈추는 걸 모르지 않도록"). 테스트 파일은 케이스마다
예외·SystemExit를 잡아 FAIL로 적고 다음 케이스로 가고, 그래도 끊기면 `TEST-HALTED`를 남긴다. `run_tests.py`가 완주·건수를
`journal/test_runs.jsonl`에 쌓는다. ★가 나오면 보고서 §6 한계 첫 줄에 적고, 고칠 수 있으면 3단에서 고친다.
*실사례: (66)-b가 검사 대상의 sys.exit에 걸려 그 뒤 케이스가 10-03~10-10 한 번도 돌지 않았는데 아무도 몰랐다.*

## 2단 진단·제안 — `propose`

산출: `analysis/피드백_<week>.md` (한국어). 뼈대는 아래 그대로 — 게이트가 제목을 글자 그대로 찾는다.

```
# 자가 피드백 — <week>
[피드백] 놓친 급등 N건 · 결함 N · 맞은 판단 N · 운 N · 규칙 변경 제안 N(자동 n · 승인 대기 n) · 지난주 변경 검증: 유지 n · 철회 n · 손실·오판 N건 · 오판 n · 일시적 n · 관찰 n
## §1 한눈에
## §2 종목별 사후분석
## §2-b 손실·시나리오 사후분석
## §3 유형별 제안
## §4 지난주 검증
## §5 적용 결과
## §5-b 실전 준비
## §6 한계
```

**§1 한눈에** — 가장 많이 새는 단 · 막은 유형 분포 · 지표 표(수집값) · 이번 주 가장 비싼 놓침 셋(최대 상승폭 × 우리가
가질 수 있었던 크기).

**§5-b 실전 준비**(2026-10-15 — 실계좌 전환 주간 · 사용자: "이번 주 모의 run에서 최대한 테스트하고 문제는 토요일 trade-feedback으로 고친다") —
수집의 〈실전 준비〉 표(그 주 `real_check_<st>_<mkt>.md` — run마다 12항목)를 옮기고, **★가 나온 항목마다** 원인과 조치를 적는다:
고칠 수 있는 결함이면 §3 제안 행(유형 단위 · 반례 점검), 실계좌 전환을 막는 것(①실계좌 매수 0 · ⑦조회 오류 · ⑫전환 예행 섞임)이면
승인 대기로 보고 첫머리에. 점검표가 없는 주는 '해당 없음 — 점검표 없음'.

**§2 종목별 사후분석** — **전수 판정 표**(급등·조기 매도·늦은 매도 전부 한 줄씩: 종목 · 최대 상승·되돌림 · 1순위 유형 ·
판정 · 한 줄 근거)와 **심층 사후분석**을 둘 다 쓴다. 심층 대상은 범주로 정한다(건수로 자르지 않는다):
① 시총 상위이거나 유니버스 안인 놓침 전부 ② 보유했는데 극소 크기였던 것 ③ 조기·늦은 매도 전부 ④ 나머지는 유형마다 대표 1건.
심층은 종목마다 아래 여섯 칸이다:

```
### <티커> <이름> — 판정: <결함|맞은 판단|운>
- 무엇이 올랐나: 창·저점→고점·되돌림
- 우리 기록: 깔때기 · 막은 유형 · 평가 이력 요약(첫 등장·마지막 평가)
- 안 산·못 산 이유: 유형과 그 근거 줄(파일·절)
- 언제 무엇을 평가했어야 했나: 고점 전 날짜 + 그날 우리 기록의 단서 인용("…" — 파일·절)
- 막은 규칙: 스킬 문서 파일·절(없으면 '규칙 없음 — 아무도 평가하지 않음')
- 판정 근거: 한두 문장
```

**§2-b 손실·시나리오 사후분석** — 수집의 '손실·약세 후보' **전부**를 한 줄씩 판정한다(종목 · 논지 · 순실현 또는 평가 손익 ·
울린 시계 · 판정(오판/일시적/관찰/이익) · 오판 유형 · 한 줄 근거). 수집의 제안 판정은 출발점이지 결론이 아니다 — 바꾸면 이유를
적는다. 판정 기준은 원칙 6이다 — **시계가 안 울렸으면 손실이 커도 일시적**이다. 오판마다 아래 여섯 칸을 쓴다:

```
### <티커> <이름> — 오판 · <방향|동인|시점|가지 누락|집중|크기>
- 시나리오가 예상한 것: 논지·시나리오 원문 인용(파일·절 또는 원장 id)
- 실제로 온 것: 무엇이 언제 왔나(보도·지표 — 날짜)
- 울린 시계: ⓐ~ⓓ 중 무엇(다리 id·발화일·동인 상태)
- 진입 전 단서: 진입일 전 우리 기록에 있던 단서 인용("…" — 파일·절). 없으면 '단서 없음'(그러면 규칙 변경 근거가 약하다)
- 빠진 가지·비어 있던 규칙: 스킬 문서 파일·절
- 판정 근거: 한두 문장
```
같은 유형의 오판은 §3에서 한 행으로 묶어 제안한다. 기한 도래 전망은 hit/miss를 매기고, 오래 열린 시나리오는 유형 '가지 누락'의
근거로 쓴다. 판정 결과는 `data/feedback/손실판정_<week>.json`(`{"week", "rows": [{thesis_id, ticker, verdict, type, clock, next_check}]}`)으로
남긴다 — 다음 주 보정표와 `loss_misjudged_rate`가 이 파일을 읽는다. §4 끝에 보정표 한 줄(수집의 '지난주 판정 보정')을 옮긴다.

결함이면 **어디가 비었나**를 같이 적는다 — `rule`(규칙이 막았다) · `tool`(도구가 못 봤다·기록이 비었다) ·
`universe`(감시 밖이었다) · `param`(크기·문턱 숫자) · `safety`(안전장치). 이것이 제안의 `kind`가 된다.

**§3 유형별 제안** — 같은 원인의 결함을 한 행으로 묶어 원장에 올린다. 결함이 아닌 판정도 기록한다(`change` 없이) —
다음 주에 같은 규칙을 다시 흔들지 않기 위해서다.

```
python3 feedback.py propose add --file data/feedback/제안_<week>.json    # 행 배열 · 거부되면 사유가 나온다
```

행 필드: `kind` · `verdict` · `evidence[{ticker, market, ret, window, blockers}]` · `cause`(유형 문장) ·
`change{file, section, summary}`(결함만) · `expected{metric, baseline, target}`(지표는 수집 §지표의 키 · baseline은 수집값) ·
`next_check{date, metric}`(보통 다음 토요일) · `note`.
§3에는 원장이 준 `FB-<week>-<n>` id로 표를 쓴다: id · 종류 · 원인 · 변경 · 기대 효과 · 권한(자동/승인 대기) · 반례 점검.

**반례 점검(제안마다 필수)** — 그 규칙이 이번 창에 이미 있었다면 **손해를 봤을 종목**이 수집에 있는가를 찾아 적는다
(예: 재진입 조건을 걸었다면 되돌림이 큰 종목에서 고점 근처에 다시 샀을 것). 반례가 이득보다 크면 제안을 내리거나
조건을 좁힌다. 반례를 못 찾았으면 "찾지 못함 — 찾은 범위"를 적는다.

**게이트 전 자가 감사** — `<REPO>/.claude/skills/_stepgate/audit_rubrics/trade-feedback.json`의
렌즈(비봉인 — 읽어도 된다)를 보고서에 스스로 적용하고 결과를 §6에 한 줄씩 적는다. 위반이면 고치고 게이트로 간다.

게이트: `SG judge trade-feedback propose <id>=<값> … week=<YYMMDD> deliverable=<피드백 md 절대경로> dir=<프로젝트폴더>`

## 3단 적용 — `apply`

```
python3 feedback.py status                         # 승인 대기 · 적용 가능 목록
python3 feedback.py verify --week <YYMMDD>         # 지난주 적용분 — 유지 후보 / 철회 후보
```

1. **자동(`auto`) 행만 적용한다.** 스킬 문서를 고칠 때는 **반드시 `Skill(skill-maintainer)`를 먼저 호출**하고 그 절차대로
   (백업 · `lossless_assert` · `check_skill_integrity.py` · `SG judge skill-maintainer verify` GATE PASS · `cleanup_backups.py`).
   규칙을 바꾸면 **같은 편집에서 셋을 같이** — ① 문서 ② 봉인 루브릭(값을 출력하지 않는 스크립트) ③ `req_audit.py` 행
   (폐지면 금지 앵커 `NOT:`). 코드를 고치면 파일마다 백업 → `code_edit_check.py <백업> <파일>` 종료코드 0(skill-maintainer §2) →
   `python3 run_tests.py`로 테스트를 돌리고 **완주·실패 0**을 확인한다 —
   멈춤·건수 감소가 나오면 그 뒤 케이스가 안 돈 것이니 고친 것을 검증했다고 쓰지 않는다.
   적용한 행은 `python3 feedback.py propose set --id <id> --status applied --note "<무엇을 바꿨나>"`.
2. **승인 대기(`confirm`) 행은 적용하지 않는다** — 원장이 `applied` 표시를 거부한다. 보고에 한 줄씩 올린다
   (무엇을 · 왜 · 승인하면 무엇이 바뀌나). 사용자가 승인하면 `--status confirmed` 뒤에 위 1번 절차로 적용한다.
3. **지난주 적용분 검증** — `verify`는 **적용일 이후 사건만으로 다시 잰 '적용 후 값'**으로 판정한다(창 지표는 참고로만 —
   20거래일·14일 창의 대부분이 적용 전이면 적용 전 매도만으로 '철회 후보'가 나온다. 2026-10-10 · FB-261010-4).
   `유지 후보`면 `--status verified`, `철회 후보`면 skill-maintainer 절차로 되돌리고 `--status reverted`, `미측정·변화 없음`이면 검증일을 한 주 미루고 그 사실을 §4에 적는다.
   되돌리기가 규칙 삭제·숫자 상수 변경이면 정책상 승인 대기다 — 되돌리지 말고 §5 승인 대기에 이유와 함께 올린다.
   그 지표가 이번 주에 고친 측정 결함 위에 있었으면 판정하지 말고 미룬다. 미루기: `python3 feedback.py propose set --id <id> --next-check <다음 토요일 YYYY-MM-DD> --note "<이유>"`.
4. **`config/limits.json`·`watchlist.json`을 바꾸면** 이유를 원장 `note`와 CHANGELOG에 남긴다 — 다음 매매 run이 §10에 공개한다.
5. **`CHANGELOG.md`에 이번 피드백 항목을 매번 남긴다**(적용 0건이어도): `## YYYY-MM-DD — 자가 피드백 FB-<week>` 아래
   적용 · 승인 대기 · 검증 결과를 행 id로.
6. **게이트 승격 — 매매 run의 감사에서 반복해 잡힌 유형을 게이트 문항으로 올린다.** 매매 run은 fact-check 감사를 최대 두 번
   받고, 2차 결과로는 고치지 않는다. 남은 지적은 승격 원장에 lens별로 쌓인다. 이 단계가 그것을 게이트로 올리는 자리다 —
   run이 자기 게이트를 고치면 게이트가 독립성을 잃으므로 run에서는 하지 않는다.
   ```
   python3 <REPO>/.claude/skills/_stepgate/stepgate.py findings fact-check for=trade-run
   ```
   `★ 승격 대기`(서로 다른 두 run 이상)마다 skill-maintainer 절차로 ① 봉인 루브릭에 두 극성 문항 하나를 스크립트로 더하고(값 비출력 ·
   문항 문구는 비봉인 `audit_rubrics/fact-check.json`의 그 lens에서) — **판정표 품질 lens는 `fact-check.json`의 `verdict`**(판정표를 만든 쪽이
   답하고 모든 호출자에 걸린다), trade-run 고유 유형만 `trade-run.json`의 `note` — ② `req_audit.py` 행을 넣고
   ③ `python3 <REPO>/.claude/skills/_stepgate/stepgate.py promoted fact-check lens=<id> into=<fact-check:verdict | trade-run:note> note=<문항 id>`로
   기록한다(2026-10-08 · 같은 lens를 호출자 게이트마다 복제하면 문항 id가 갈라진다). 원장 FB 행으로도 남긴다(kind `tool`, 다음 주 검증 지표는 그 lens의 재발 run 수).
   **문항 수 상한은 없다** — 반복되는 문제가 쌓이면 문항은 계속 는다. 산출물에 'N개 이상' 같은 분량 할당을 거는 문항만
   만들지 않는다(분량을 미리 정하지 않는다는 원칙). 남긴 대기 건은 이유를 보고서 §5에 적는다.

7. **세금 — 실계좌 미국 체결이 있으면.** `python3 tax_ledger.py --year <YYYY>`가 해외주식 실현 손익(결제일 환율 · 선입선출 ·
   수수료 차감)과 예상 세액(연 순차익 − 250만 원 × 22%)을 낸다. **12월 토요일에는 `--december`**로 손실 실현 후보(보유 평가손 ·
   세금 절감액)를 §5에 표로 올리고 다음 매매 run의 매도 재료로 넘긴다 — 사람에게 묻지 않는다. 순차익이 공제 안이면 절감액은 0이고,
   손실은 다음 해로 넘어가지 않는다. 신고(5월)는 증권사 양도세 자료로 한다 — 이 원장은 추정이다.

게이트: `SG judge trade-feedback apply <id>=<값> … week=<YYMMDD> deliverable=<피드백 md 절대경로> dir=<프로젝트폴더>`

- [ ] `collect` · `propose` · `apply` GATE PASS 세 줄
- [ ] 놓친 급등 · 조기 매도 · 늦은 매도 **전부**가 §2 전수 판정 표에 있는가(건수로 자르지 않았는가)
- [ ] **손실·약세 후보 전부가 §2-b에 있는가** · 오판마다 울린 시계(ⓐ~ⓓ)가 적혔는가 — 가격 하락만으로 오판을 준 행 0 ·
      일시적·관찰은 `next_check`로 이월 · `손실판정_<week>.json` 저장 · §4 보정표 한 줄
- [ ] 결함 판정마다 **고점 전 날짜의 단서 인용**이 있는가 — 사후 지식으로 채점한 행 0 · 고점 전 기록이 아예 없는
      커버리지 결함(원칙 2)은 단서 칸에 그 사실을 적는다
- [ ] 제안 문장(`cause`)에 종목 고유명사 0 · 제안마다 반례 점검
- [ ] 승인 대기 행을 적용하지 않았는가 · 적용 행마다 문서·루브릭·`req_audit` 셋이 같은 편집에 있는가 · `next_check`가 있는가
- [ ] `CHANGELOG.md`에 `FB-<week>` 항목
- [ ] **게이트 승격** — `findings fact-check for=trade-run`의 승격 대기 0, 또는 남긴 건마다 §5에 이유
- [ ] `python3 req_audit.py` 누락 0
- [ ] `python3 run_tests.py` 완주(★ 없음) — ★면 §6 한계 첫 줄
