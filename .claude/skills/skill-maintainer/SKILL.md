# Skill Maintainer (스킬 유지·보수·개편)

> ### ▶ 단계 게이트 (필수 — 합격은 네가 아니라 *심판*이 판정한다)
> hook 차단 환경의 강제 레버. 헬퍼 `SG` = `python3 <REPO>/.claude/skills/_stepgate/stepgate.py`.
> 편집 마무리 전 체크포인트: ① `SG form skill-maintainer verify` 로 관찰 항목을 받아 → ② **정직히** 답한 뒤(합격 기준 비공개·**표현이 회차마다 뒤집히니 지난 답을 재사용하지 말고 이번 문구를 그대로 읽고 답할 것**) → ③ `SG judge skill-maintainer verify <id>=<값> ...`. **GATE PASS가 아니면 마무리 금지**(말로 'done' 불가).
> 체크포인트: **verify**(백업·무손실·보호 스킬 미수정). 게이트 루브릭 파일은 직접 열람 금지(열람 시 무효 — Read는 감사됨). 상세 규약: 아래 〈단계 게이트 프로토콜〉.
> `<REPO>` = 이 저장소를 클론한 **절대경로**(문서상 표기). `dir=`·`deliverable=`은 절대경로여야 하므로 호출할 때 실제 경로로 치환한다.

스킬 파일(`SKILL.md`·`scripts/`·`references/`) 자체를 안전하게 손보는 메타스킬. 두 원칙이 전부다:

1. **"스킬을 고쳐라"** — 산출물의 반복 실수는 일회성 수습이 아니라 **스킬에 규칙으로 박아** 재발을 막는다(뒤늦은 수습은 의미 없음).
2. **검증 가능한 무손실** — 구조를 바꿀 때 *내용이 한 글자도 사라지지 않았음*을 **기계적으로 증명**(assert/grep/byte-delta)한 뒤 끝낸다. "아마 괜찮음"은 실패.

## 0. 시작 전 — 대상 이해 + 게이트 + 보호 스킬 + 환경

**대상 스킬 먼저 통독·이해 (★ 손대기 전 선행)** — 편집·개편 전에 그 스킬을 *먼저 이해*한다. 안 그러면 **중복·모순 규칙을 박거나 암묵적 설계를 깬다.**
- **SKILL.md 전체 통독**: 목적·트리거(`description`)·섹션 구성·이미 있는 규칙.
- **`scripts/`·`references/` 역할 파악**: 각 스크립트/헬퍼가 무엇을 하는지, 함수 시그니처·섹션 간 의존, **왜 이 구조인지**(설계 의도).
- **추가하려는 규칙이 이미 있는지 먼저 확인** — 있으면 보강, 없을 때만 신설(중복·모순 방지). `Grep`로 키워드 검색.
- 경량 편집도 최소 **관련 섹션은 읽고** 손댄다. 이 이해 위에서 아래 게이트를 판단.

**경량 vs 중량 게이트** (과정 비대화 방지):
- **경량**(규칙 한 줄·문구·체크리스트 항목 추가) → 그냥 `Edit`. 아래 프로토콜 불요.
- **중량**(구조 개편·리네임·가이드 흡수·스크립트 수정·신설/fork) → 해당 절차(§1~§6) 적용.
- **코드(.py)는 한 줄을 고쳐도 경량이 아니다 → 항상 §2.** 스킬 문서가 **호출하는** 프로젝트 코드도 포함한다(아래 §2 첫머리).

**보호 스킬 — 원본 수정 금지**: `deckster-slide-generator` · `dart-analysis`(팀 공유·안정). 손봐야 하면 **사본/신설로**(원본 불변). 예: `dart-analysis-code`는 원본을 건드리지 않고 엔진만 공유. cf. [[dart-analysis-code-skill]]

**환경 사실**:
- 스킬 위치 `<폴더>/.claude/skills/<name>/` — **폴더 스코프**. 루트 `.claude/skills/`는 전역, 하위 폴더(`work/other-workplace`·`work/consulting`·`life`)의 것은 그 폴더에서 작업할 때만 로드된다. **폴더명 = 호출명 = 트리거 매칭 단위**. frontmatter `description`이 활성화 트리거다.
- **★ 스코프 배치 기준 — 대상이 *도메인*이면 하위 폴더, *다른 스킬·워크플로 자체*면 루트 전역.** 스킬이 특정 업무 도메인(클라이언트·산출물 양식·특정 데이터소스)을 다루면 그 폴더에 두고, **메타 스킬**(다른 스킬을 고치거나·심판하거나·공용 엔진을 제공)은 **루트**에 둔다 — 하위 폴더에 두면 *다른 스코프에서 일할 때 사라져서* 그 스코프의 스킬들이 자기를 호출하지 못한다. **리트머스: 이 스킬을 `life/`에서도 `work/other-workplace/`에서도 부를 일이 있는가 — 있으면 루트.** *실사례: `gate-audit`(전 스킬의 게이트 심판자)이 `work/consulting/`에 있어, life 스킬 `fact-check`의 FIRE 블록이 비동기 감사를 띄우려 해도 gate-audit이 로드되지 않았음 → 루트로 이동.* 현 루트 전역: `skill-maintainer`·`gate-audit`·`writing-style`·`gemini-image` + 지원 디렉터리 `_stepgate`·`_shared`.
- python은 `& "python3"` 셔임 — **인자에 `|` 등 cmd 메타문자 금지**(cmd 파이프로 깨짐). cf. [[python-env-setup]]
- 이 PC는 관리정책으로 **사용자 hook 전부 차단** — 자동화는 hook이 아니라 스킬/설정으로. cf. [[managed-policy-blocks-hooks]]

## 1. 무손실 구조 개편 (reorg) ★

비대한 스킬을 **기능 단위로 유형화**할 때. 단 절대 유실 금지.

1. **백업(복원점 스크래치)** — `_<skill>_SKILL_backup_YYMMDD.md`로 직전 상태 보존(복원/대조용). **★ 대상 스킬 폴더 절대경로에 생성**(`...\skills\<name>\` 안) — bare 파일명은 cwd(리포 루트)에 떨어져 흩어진다(루트에 14개 쌓였던 원인). 산출물처럼 영구 누적하진 않되 **스킬별 최신 1개는 복원점으로 유지**하고 중간 단계만 §7로 청소. cf. [[deliverable-versioning]]는 *산출물* 규칙이지 이 스크래치엔 적용 X.
   - **★ 덮어쓰지 말고 붙여라 — 파일명이 날짜뿐이면 같은 날 두 번째 편집이 그날의 복원점을 지운다.** `cp`는 확인 없이 덮으므로 **먼저 존재를 확인하고, 있으면 날짜 뒤에 글자를 붙인다**(`…_260910.md` 다음은 `…_260910b.md`). 한 줄로: `[ -e "$B" ] && B="${B%.md}b.md"; cp SKILL.md "$B"`. 접미사는 `_backup_` **뒤**에 오므로 lineage(§7의 그룹 키)가 갈라지지 않는다. *실사례: 같은 날 두 번째 편집이 `cp`로 그날 아침의 개편 전 스냅샷을 덮어썼고, 그 스킬 폴더가 git 미추적이라 복구 경로가 없었다.*
   - **★ 백업은 git을 대신하지 못한다.** 미추적 폴더의 스킬은 복원점이 이 파일 하나뿐이다 — 구조 개편처럼 되돌릴 수 있어야 하는 편집 전에는 **그 폴더가 추적되는지 확인**하고, 아니면 사용자에게 커밋을 제안한다.
2. **블록 파싱** — `##`/`###` 경계로 블록 분해(**코드펜스 ``` 안의 `#`은 헤더 아님** — fence-aware).
3. **범주 재배치** — **사용자의 기존 분류축**(또는 자명한 기능축: 내용구성/형식/워딩/출처/빌드/점검 등)으로 묶음. **임의 프레임(렌즈1/2 등) 발명 금지** — 소통 안 됨. cf. [[organize-by-user-taxonomy]]
4. **완전성 검증** — `python scripts/lossless_assert.py <백업> <개편본>`으로 **removed=0**(순수 reorg면 사라진 줄 0) + **byte-delta = 추가한 배너만큼만** 확인. removed가 있으면 각 줄이 *의도한 편집*인지 1:1 대조.
5. **프론트매터 무결** — line 1~ `---name:…---` 그대로(깨지면 스킬 로드 실패).
6. **cosmetic은 별도** — "N차" 라벨·비연속 번호 정리는 **헤더만** 바꾸고 본문 불변(다시 §4로 검증).
7. **★ 백업 청소(검증 후 필수)** — `lossless_assert` removed=0 + 자가점검을 통과했으면 중간 단계 백업은 수명 종료다 → `python scripts/cleanup_backups.py --apply`로 정리. **★ 스킬별(파일명 `_backup_` 앞부분 = lineage) 최신 1개는 복원점으로 자동 보존**, 그보다 오래된 것만 삭제(전부 지우려면 `--purge` — 예외·위험). 진행 중 다른 세션은 `--keep-days 1`로 추가 보호. 기본 DRY-RUN(목록 먼저 확인). **편집 마무리 루틴에 항상 포함**(손삭제 누적이 문제였음). 기본 스캔 = **리포 안의 모든 `.claude/skills` 재귀 + 리포 루트 직속 + 전역 `~/.claude/skills`**(스크립트 위치에서 리포 루트를 역산 — 경로 하드코딩 없음) — `_*_backup_*`(.md·.py 등) 매칭, `_archive_`(§4 의도 이관본)는 자동 제외.

## 2. 헬퍼/스크립트 코드 수정 ★

**대상** — 스킬 폴더의 `scripts/`만이 아니다. **스킬 문서가 호출하는 프로젝트 코드도 그 스킬의 스크립트다**
(예: `trade-run`이 부르는 `life/ai-trading-bot/*.py`). 문서만 이 절차로 고치고 코드는 따로 고치면 안 된다.

**절차 — 코드 파일 하나마다 이 순서를 건너뛰지 않는다:**
1. **백업** — 고칠 파일과 같은 폴더에 `_<파일명>_backup_YYMMDD.py`(있으면 `b`·`c`를 붙인다 — §1과 같은 규칙). 백업이 없으면 2~4를 할 수 없다.
2. **함수 먼저 Read** → 타깃 `Edit`. 스크립트로 블록을 통째 치환할 때 특히 위험하다 — 새 블록에 원래 줄을 안 옮기면 그 줄은 **조용히 사라진다.**
3. **`python3 <이 스킬>/scripts/code_edit_check.py <백업> <파일>`** — 컴파일 + 사라진 줄을 **함수별로** 보여 준다. 사라진 줄마다
   `--ok "<그 줄 일부>"`로 의도한 삭제·교체임을 밝혀 **종료코드 0**을 받는다. `★ 'x' 대입이 사라졌는데 같은 함수에서 아직 읽힌다`가 뜨면
   그 줄을 옮기지 않은 것이다 — `--ok`로 덮지 말고 되살린다.
4. **그 프로젝트의 테스트 러너**를 돌려 완주·실패 0(예: `life/ai-trading-bot/run_tests.py`). **주문·전송·외부 쓰기 경로를 고쳤으면
   그 경로를 끝까지 도는 테스트가 있어야 한다** — 없으면 만든다(가짜 클라이언트로 전송부터 결과 기록까지). 고친 함수를 아무 테스트도
   부르지 않으면 "테스트 통과"는 아무것도 증명하지 않는다.
5. **새로 만든 `.py`**는 백업 대신 `code_edit_check.py --new <파일>`로 기록한다.
6. **감사는 디스크로 한다** — `code_edit_check.py`는 실행마다 `_stepgate/code_edit_log.jsonl`에 (파일·백업·해시·사라진 줄·종료코드)를 남기고,
   **verify 게이트의 디스크 기준(`code_audit`)**이 `scripts/code_edit_audit.py`로 "기준선 뒤 바뀐 `.py`마다 ① 지금 해시로 통과한 검사 기록
   ② 같은 폴더 백업 ③ 수정 뒤 테스트 러너 완주"를 대조한다. **위반이 있으면 답과 무관하게 GATE FAIL** — 검사를 건너뛰고 "돌렸다"고 답할 수
   없다. 마무리 전에 `python3 <이 스킬>/scripts/code_edit_audit.py`로 미리 본다. 검사 뒤 파일을 또 고치면 다시 검사해야 한다(해시가 다르다).
   다른 세션이 검사 없이 고친 파일은 내용을 확인한 뒤 `code_edit_audit.py --adopt <파일> --why "<무엇을 확인했나>"`(기록이 남고 감사 출력에 '인수'로
   보인다). 감사 범위는 모든 `.claude/skills` + `_stepgate/code_audit_roots.json`에 등록한 프로젝트 폴더(스킬이 새 프로젝트 코드를 부르면 등록한다).
*실사례(2026-10-12): `execute._send_orders` 블록을 치환하며 `res = place(client, o)` 한 줄이 빠졌다. 문법 검사·테스트 130건이 편집 24분 뒤에도
통과했고(그 함수를 부르는 테스트가 0건), 그날 밤 예약 run의 주문 전송이 전부 UnboundLocalError로 죽었다. 문서 5개에는 lossless를 돌리고
코드 19개에는 안 돌린 것이 원인이다 — 3번이 그 줄을 `-[1] L440 res = place(client, o)`로 바로 짚는다.*

**코드 공통 규칙:**
1. **함수 먼저 Read** → 타깃 `Edit` → **`py_compile`/import로 구문 검증** → 가능하면 실제 빌드 1회.
2. **★ 공유 절대경로 계약** — `research-organizer/scripts/styles.py`는 **여러 빌드스크립트가 절대경로로 import**한다. 시그니처·함수명·경로를 깨면 전 빌드가 죽음 → 추가는 OK, 제거/개명은 ripple 확인.
3. **레이아웃·매직넘버 하드코딩 금지** — 헬퍼로(검증 가능하게). cf. [[skill-first-build]]
4. 코어 함수(모든 빌드가 쓰는 것) 수정은 회귀 위험 큼 → 보수적으로, BOX/fill 등 판정 추가는 부작용 점검.

## 3. 리네임 (folder = invocation)

1. **폴더명 변경 = 호출명 변경.** 한 곳만 바꾸면 안 됨. frontmatter `name:`도 **같이** 바꾼다(폴더명≠name이면 스킬이 조용히 안 뜬다).
2. **★ 봉인 루브릭·audit_rubric도 이름으로 조회된다 — 리네임하면 게이트가 죽는다.** `_stepgate/rubrics/<name>.json`·`audit_rubrics/<name>.json`은 **스킬 이름이 키**다. 폴더만 바꾸면 새 이름의 루브릭이 없어 `SG form/judge <새이름> <cp>`가 실패하고, **옛 이름 루브릭은 고아로 남는다**. → 새 이름으로 **파일을 옮기거나 새로 작성**한다(작성 시 기존 루브릭 파일을 *열지 말고* 〈단계 게이트 프로토콜〉의 스키마로; **항목마다 Y/N 두 극성 `variants` 필수**). *실사례: `knowledge-map`→`life-map` 리네임 후 루브릭이 안 따라와 정식 게이트가 통째로 죽어 있었음(스크립트가 잡아냄).*
3. **ripple grep** — 다른 스킬·**빌드스크립트 하드코딩 경로**·메모리·핸드오프에서 옛 이름 전수 검색→갱신(`Grep`로 스킬 루트 전체). **★ 자매 스킬 포인터 주의**: 같은 기능의 다른 스코프 버전을 가리키는 참조는 *옛 이름 그대로 두어야 맞다* — 일괄 치환하면 형제 포인터가 깨진다. **자기 참조만** 바꾼다.
4. **description 동시 갱신** — 트리거 문구가 이름과 어긋나지 않게. 자매 스킬이 있으면 **스코프 구분 문구**도 갱신.
5. **★ 마무리는 정합성 스크립트로 증명** — `python3 <REPO>/.claude/skills/_shared/check_skill_integrity.py` → **OK 아니면 리네임 미완료**(눈으로 훑지 말 것).

## 4. standalone화 (외부 가이드 흡수)

원칙: 스킬은 **스킬 폴더 밖(리포 루트 등)의 가이드에 의존하지 말 것**(단독 실행).
1. **번들** — 가이드를 스킬 `references/`로 **복사**(88KB 가이드를 SKILL.md에 인라인 재작성하면 유실 위험 ↑ → 번들이 안전. 사용자 규칙: "가이드가 스킬 폴더 안에 있으면 같이 써도 됨").
2. **경로 재지정** — SKILL.md의 스킬 폴더 밖 가이드 참조를 `references/…` 상대경로 또는 교차스킬 포인터로.
3. **암호 태그 평문화** — `(가이드 §X)`·`(방법론 B-1·E-3)`는 "동봉 가이드의 앵커"라고 intro에서 명시(또는 핵심만 인라인 풀이). 용어 통일(가이드 vs 방법론 혼용 금지).
4. **검증** — `Grep`로 외부 가이드 경로 의존 **0** 확인. 원본 가이드는 `_archive_…`로 **이관(삭제 아님)** + 지식지도 갱신.

## 5. 세션 피드백 반영 루프

1. 피드백 파일(`_스킬피드백_*.md`) → **스킬별 트리아지**(어느 스킬의 무엇).
2. **★ 일반화 필터 — *그 작업 특수 내용*을 규칙으로 박지 말 것(개념화 강제).** 세션 교훈을 스킬에 반영할 때, *이번 과제의 고유 사례*(이번 firm·이번 거래·이번 수치·이번 도메인)를 그대로 규칙 문장으로 넣으면 다른 맥락엔 안 쓰이는 죽은 규칙이 된다. **그 실수가 *어떤 일반 오류 유형*인지로 한 단계 추상화**해 다른 맥락에도 성립하는 원칙으로 쓰고, 특정 사례는 *짧은 예시(`실사례:`)*로만 붙인다. **리트머스: 규칙 문장에서 도메인 고유명사를 다른 것으로 바꿔도 규칙이 성립하는가** — 안 되면 아직 과제 특수 내용(추상화 부족). (실사례: 'GFO-X 거래는 OTC 아님'(과제 특수)을 → '분류·귀속은 표면 신호가 아니라 *범주를 가르는 결정 속성*으로 검증'(일반 원칙)으로 추상화 — OTC 도메인 밖에서도 성립.)
2-bis. **★ 명료성·정리 필터 — 덧붙이지 말고 *개선 방향*을 지시하라.** 스킬에 넣는 규칙은 *'다음엔 이렇게 하라'*가 한눈에 읽히는 **명령형 지침**이어야 한다 — 장황한 설명·메타 서술('A는 B의 확장'·'X 비대칭의 false-negative' 류)·읽어도 행동이 안 바뀌는 문장 금지(**리트머스: 그 문장 하나로 다음 작업을 *다르게* 할 수 있는가** — 없으면 다시 써라). 또 세션마다 '+X'만 덧대면 스킬이 군더더기 더미가 되니, 새 규칙은 *맞는 섹션에 깔끔히* 넣고 한 항목에 누적돼 비대하면 **그 자리에서 무손실 통합**(중복 병합·압축)한다(*추가 = 정리와 한 쌍*). 이 기준을 **여러 스킬 전반에 적용해 톤을 통일**한다. *실사례: '능력-커버리지 비대칭의 false-negative'(난해)를 '비교는 모든 대상을 같은 깊이로 조사하라; 못 찾음은 없음이 아니다'(명령형)로 고쳐 씀.*
3. 반영 시 **근거(왜)·적용법 보존** — 규칙만 박지 말고 이유를 남겨야 미래에 안 지워짐.
4. **반영 현황 stamping**(✅완료/⏳잔여) — 여러 턴/스킬에 걸치면 추적 가능하게.
5. **워딩 변경·구조 변경은 사용자 컨펌 후.** 비자명한 결정은 메모리에 저장. cf. [[deliverable-storyline-lead]]

## 6. 스킬 신설 / fork

- **신설**: 명확·구체적인 트리거 `description`(사용자 실제 표현) + `scripts/`·`references/` 구성.
- **fork(사본)**: **드리프트가 최대 리스크.** 공용 엔진은 **복사하지 말고 절대경로로 공유**(예: `dart-analysis-code`가 `dart-analysis`의 `analyze.py` 등을 절대경로 호출 — 엔진 수정은 원본 한 곳). 환경/워크플로우 차이만 얇게 분기.
- **트리거 중첩 주의**: 두 스킬이 같은 의도에 반응하면 `description`으로 **환경/스코프 구분**(완전 분리하려면 한쪽 트리거 축소 — 보호 스킬이면 사용자 GO).
- **버저닝**: 산출물 덮어쓰기 금지, 항상 버전 발행. 표기 **`vN_M`**(N=앞=주요/사인오프, M=뒤=경미). **★ 이관 규칙: ① M++(경미)일 때만 직전 minor를 `이전버전\`으로 이관(메인엔 현 major의 최신 minor 1개만) ② N++(주요)일 때는 직전 major를 메인에 보존(이전버전 이관 X — 주요 버전은 누적) ③ 주요 버전(N)이 메인에 **5개를 넘게** 누적되면 가장 오래된 major부터 `이전버전\`으로 이관(메인엔 최근 ~5 major).** 예: v1_0→v1_1=v1_0 이관 / v1_2→v2_0=v1_2 메인 유지. **★ 예외 — 날짜가 계속 늘어나는 일지형 산출물**(파일명에 날짜가 박히고 매일 새 건이 생기는 것)은
위 ②를 적용하지 않는다. 날짜마다 major까지 쌓으면 메인 폴더를 곧 못 읽는다 → **날짜당 최신 1개만 메인,
나머지는 major·minor 불문 `이전버전\`으로.** 이 판정은 기억이 아니라 **스크립트로** 강제한다.
*실사례: `world-study`의 `세상공부_YYMMDD_vN_M.md` → `tidy_versions.py`.*
**flat 번호(v1·v2…) 금지**(major/minor 구분이 사라짐), **전 산출물 동일 규칙 일관 적용**(.md만 다 남기고 docx만 이관하는 식 금지). 구버전 보존(삭제 아님). cf. [[deliverable-versioning]]

## 단계 게이트 프로토콜 (다단계 스킬 강제 — 재사용 규약)

hook 차단 환경([[managed-policy-blocks-hooks]])에서 다단계 스킬의 *단계 건너뛰기*를 막는 **보고자/심판 분리 + 봉인 루브릭** 메커니즘. 스킬은 *읽히지만* 행동 순간 단계를 조용히 스킵한다 — 강제력은 hook 없이 소프트뿐이라, **눈에 보이는 산출물 assert + 판정 외부화**로 흉내 낸다.

**★ 2티어 + 해소 (속도·커버리지 동시 — 2026-06-27 개편)** — 인라인 escalate 서브에이전트(체크포인트당 ~45s 블로킹)가 느리고, 봉인 루브릭이 가이드 4~9개 *표본*만 봐서 나머지가 샜다. 그래서 심판을 **빠른 인라인 바닥(T1)** 과 **느리고 빡빡한 비동기 가이드 심판(T2)** 으로 쪼개고, 전달 경계에 **해소 게이트(T3)** 를 둔다. T2는 크리티컬 패스 밖(다음 작업과 중첩)이라 시간 압박 없이 *전체 가이드*를 적대적으로 본다.

**네 역할 분리**
1. **워커**(스킬 실행 모델): 체크포인트에서 `form`으로 *관찰 항목만* 받아 정직히 답한다 — **합격 기준은 모른다**(teach-to-test 억제).
2. **결정론 심판 = T1 바닥**(`stepgate.py judge … async`): 워커가 안 보는 **봉인 루브릭**으로 디스크 재검증+attest/quote+순서 토큰만 ~5s에 판정(escalate 서브에이전트 *없음*) → 즉시 GATE PASS + 감사 큐 적재(enqueue) + FIRE 블록. 워커는 백그라운드 감사를 띄우고 다음 작업으로.
3. **비동기 빡빡 감사 = T2**(**general-purpose 백그라운드 에이전트**에 FIRE 위임 + `stepgate.py audit-judge`; ★ gate-audit은 Skill이라 `subagent_type`이 아님): 비봉인 `audit_rubrics/<skill>.json`의 *전 lens*로 산출물을 적대적 검수 — **위반 라인/셀좌표/캡션을 그대로 인용 못 하면 그 lens는 PASS**(cite-or-pass). `needs_fetch` lens는 링크를 실제 WebFetch. 결과를 `--record`로 큐에 기록. 시간 압박 없으니 *빡빡할수록 좋다*.
4. **해소 게이트 = T3**(`stepgate.py resolve`): 사용자 사인오프 *직전*, 이 워크플로의 활성 감사가 전부 PASS인지 확인 → **RESOLVE PASS 아니면 'done' 금지**(HOLD=동기 드레인·FAIL=새 vN_M 수정·재감사). 비동기 탐지를 전달 경계에서 다시 하드 예방으로 전환.

(레거시 `escalate:true` 경로는 mode 미지정 루브릭에 한해 그대로 동작 — `judge`가 `NEEDS-JUDGE`→subverdict. `mode:"async"`면 escalate를 건너뛴다. 빠른 자체 점검 스킬(skill-maintainer·gate-audit의 self-gate)은 async 비대상 — 콘텐츠 산출물 스킬만 async.)

**엔진·경로(공유 절대경로 계약 — styles.py와 동일, 깨면 전 게이트 죽음)**
- `_stepgate/stepgate.py` — `init`/`form`/`judge`/`clear`(동기) + `enqueue`/`audit-judge`/`resolve`/`audit-status`(비동기) + `audit`(사후). 다른 스킬이 *절대경로*로 호출(시그니처·명령 유지·신규는 전부 가산).
- **호출 형태** — 스킬 문서의 `SG`는 약칭일 뿐이다. **셸 변수로 만들지 말 것**(`SG="python3 …"; $SG …`은 zsh가 `$SG`를
  한 단어로 넘겨 `no such file`이 난다 — 2026-09-16). 매번 `python3 <전체경로>`를 그대로 친다. `audit-judge --record`의
  `evidence`는 **산출물에서 그대로 복사한 20자 이상 문구 하나**(URL `…` 축약·여러 인용 이어붙이기는 거부된다).
- **★ 승격 원장 — 감사에서 반복해 잡히는 유형은 게이트로 올린다(2026-10-07).** 감사 큐는 `clear`로 지워지므로 반복을 셀 수 없었다.
  이제 `audit-judge --record`가 결과를 `_stepgate/promotion_ledger.jsonl`에 영구로 남긴다(FAIL이면 `lenses=<id,…>` 필수).
  `SG findings <스킬[,스킬]> for=<대상 스킬>` → **서로 다른 두 run 이상에서 걸린 lens = 승격 대기**. 올리는 곳은 기계로 셀 수 있으면
  검사 스크립트, 아니면 대상 스킬의 봉인 루브릭 문항(두 극성) — 올린 뒤 `SG promoted <원 스킬> lens=<id> into=<대상:cp|스킬:lint…>`로 기록.
  **봉인 문항은 열지 않고 엔진 명령으로 고친다** — `SG rubric-add <스킬> <cp> spec=<json> [mode=async]`(두 극성 `variants`가 아니거나
  이미 있는 id면 거부 · 병합본을 `validate_cp`로 검사한 뒤 백업 후 기록)·`SG rubric-drop <스킬> <cp> ids=<a,b>`. 출력은 id·백업 파일명뿐이다.
  봉인 파일을 Read·셸로 열면 R2(정답지 열람)에 걸리고, 같은 세션의 게이트 통과까지 의심받는다(2026-10-08 도입).
  원 스킬이 `fact-check`인 판정표 품질 lens는 호출자 게이트에 복제하지 말고 `fact-check:verdict`로 올린다(호출자 게이트엔 그 스킬 고유 문항만).
  **감사는 관측, 게이트는 관문** — world-study는 감사를 매 run 백그라운드로 돌리되 resolve·재감사 없이 원장 기록용으로만 쓴다
  (판정이 바뀌는 지적만 그 run에서 한 번 교정). 관문으로 쓰면(통과 전 완료 금지·재감사 반복) run당 수 시간이 든다 — trade-run 실측.
- **봉인** 루브릭 = `_stepgate/rubrics/<skill>.json`(워커 컨텍스트 밖 — SKILL.md가 참조 안 함). **비봉인** 빡빡 검수 lens = `_stepgate/audit_rubrics/<skill>.json`(gate-audit 감사자가 *읽는 게 정상* → R2 제외). verdict 토큰·감사 큐(`audit_queue/<wfid>.jsonl`)·wfid는 `%TEMP%\claude_stepgate\`(순서·해소 강제용·`init`/`clear`로 청소).

**봉인 루브릭 스키마** — `{ "<cp>": { "intent", "mode"?:"async", "after"?, "observations":[{"id","variants":[{"ask","must"}]}|{"id","ask","attest_must"?,"check"?:"quote"}], "criteria":[{"check":"files|contains|exists|xlsx_links", ...}] } }`. 검사: `files glob/min` · `contains file/pat/min` · `exists path` · `xlsx_links`(하이퍼링크·R# 셀패턴 카운트). `mode:"async"`면 judge가 바닥만 보고 escalate 대신 *감사 큐 적재*(워커는 `judge … deliverable=<abspath>` 필수). attest 항목은 미검증(정직 라벨)이되 요구 정답과 다르면 차단. **표본 추출 없음 — 모든 관찰 항목이 매 회차 전부 출제된다**(기준이 그 회차에 빠지는 일 없음; 구 `pool_n`은 폐기).

**비봉인 audit_rubric 스키마** — `{ "<cp>": { "deliverable_glob", "global_directives":[…], "lenses":[{"id","ask","severity","cite_or_pass":true,"needs_fetch"?}] } }`. lens = 그 스킬의 *전체 가이드 표면*(SKILL.md 가이드 + 피드백 메모리에서 시드). **계속 자라는 검사표** — 새 교정이 나오면 lens로 승격(`harvest-corrections-into-skills`를 audit_rubric 갱신으로 연결). 없으면 gate-audit이 SKILL.md 가이드로 기본 검수.

**★ 극성 회전 규칙 (정답 벡터 암기 차단 — 구 '역항목 규칙'을 대체)** — attest 항목마다 **같은 사실을 묻는 두 표현을 `variants`로 둘 다 써라**: 정답이 'Y'인 표현 하나, 정답이 'N'인 표현 하나. `form`이 회차마다 하나를 무작위로 뽑아 묻고 `judge`가 *그 표현의 `must`*로 채점한다.
- **왜** — 항목 간에만 Y/N을 섞으면(구 규칙) 각 항목의 정답이 루브릭에 영구 고정이라 `term_three_parts → Y`를 한 번 알면 그 지식이 계속 유효하다. 항목 *안에서* 극성이 돌면 정답 벡터 자체가 무의미해져 **내용을 읽지 않으면 답할 수 없다**. (FAIL이면 그 회차 출제가 폐기돼 답만 뒤집는 재시도도 막힌다.)
- **쓰는 법** — ① 두 표현이 **같은 사실**을 물을 것(다른 것을 물으면 항목이 둘로 갈라진 것이지 회전이 아니다) ② **이중부정 금지**(`~하지 않은 것이 없는가` 류 — 헷갈리면 정직한 워커도 틀리니 검사가 아니라 함정이다) ③ 예외 단서(`…이면 Y`)도 극성에 맞춰 뒤집을 것 ④ `check:"quote"` 항목은 극성이 없다(문구 대조) — 손대지 말 것.
- 예: `{"id":"term_three_parts","variants":[{"ask":"①②③을 다 적었는가 (Y/N)","must":"Y"},{"ask":"①②③ 중 빠진 용어가 있는가 (Y/N)","must":"N"}]}`
- (레거시 `ask`+`attest_must` 항목도 그대로 동작한다 — 고정 극성이라 암기에 약하니 손댈 때 `variants`로 올려라.)

**배선(콘텐츠 산출물 스킬 = async)** — ① 봉인 `_stepgate/rubrics/<skill>.json`: cp에 `"mode":"async"` + attest 항목마다 Y/N 두 극성 `variants`(극성 회전) + 검증 가능 항목은 disk criteria(빠른 바닥). ② 비봉인 `_stepgate/audit_rubrics/<skill>.json`: 전체 가이드 lens(cite-or-pass, 링크 검증은 `needs_fetch`). ③ H1 직후 **2단계 배너**: 「① `judge … async deliverable=<abspath>`→GATE PASS+백그라운드 gate-audit 발사→다음 작업 / ② 발행 직전 `resolve … deliverable=<abspath>`→RESOLVE PASS 아니면 done 금지」(취지·명령만, *기준 0*). ④ 마감 자가점검에 `GATE PASS`(바닥) + `RESOLVE PASS`(사인오프) 2줄. ⑤ 인자에 cmd 메타문자(`< > | &`) 금지·`pat`에 `<` 금지(python.cmd 셔임)·`deliverable`/`findings` 공백값은 따옴표.

**사후 감사(post-hoc)** — 게이트 미호출(R1)·봉인 정답지 열람(R2; `audit_rubrics`는 제외)·FAIL 무시(R3)·subverdict 위조(R4)·순서 위반(R5)·비동기감사 미완료(R6)·해소게이트 누락(R7)은 끝난 뒤 `stepgate.py audit`로 **룰베이스 탐지**(모델 자의 해석 0). `gate-audit`이 실행·전달(스킬 자신도 `report` cp로 게이트). 탐지지 예방 아님(R6/R7이 비동기 미완료·해소 누락을 백스톱).

**정직한 한계(과대선전 금지)** — ⓐ 여전히 소프트: 워커가 게이트를 *안 부르고* 진행하는 것까진 물리 차단 불가(단 GATE/RESOLVE 라인 부재로 *감사 가능*). ⓑ 봉인은 암호벽 아님(동일 FS) → 비밀을 디스크 재검증과 *병행*(가산이지 대체 아님). ⓒ T2 감사자도 LLM(관대 PASS 위험 → lens별 cite-or-pass·적대적 framing으로 완화, 증명 아님). ⓓ **빌드-후-미검증 구간**: 산출물 파일은 T2 완료 전 디스크에 존재 — T3가 막는 건 *사용자 사인오프*이지 *파일 생성*이 아니다("빌드됐으나 미사인오프" 구간). 워커=협조적·부주의 모델 전제(악의적 치터 아님).
