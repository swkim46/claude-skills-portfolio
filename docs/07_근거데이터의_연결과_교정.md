# 근거 데이터 — 사실의 교정과 그 사실을 쓴 판단을 연결합니다

[포트폴리오](../README.md) / [전체 구조](01_전체_흐름과_역할.md) / [검증과 개선](05_검증과_개선.md)

투자 업무에서는 한 번 조사한 사실을 여러 분석과 주문 판단에 사용합니다. 같은 문장을 문서마다 복사하면 원문이 바뀌거나 오류를 고쳤을 때 무엇을 다시 검토해야 하는지 찾기 어렵습니다. 현재 공개 구현은 입력 자료·출처·사실의 값과 버전·사용처를 연결해 이 문제를 다룹니다.

저는 조사 종류별로 필요한 항목과 그 항목을 쓸 판단을 정의하도록 요구하고 첫 설계를 반려했습니다. AI는 세부 DB와 등록·참조·교정 코드를 구현했습니다. 이 문서의 구현 근거는 공개 투자 코드의 2026년 10월 20일 기준본입니다. 학습 노트나 리서치 보고서를 모두 같은 DB에 넣었다는 뜻은 아닙니다.

## 현재 자료가 연결되는 방식

| 단계 | 남기는 것 | 이어지는 사용 |
|---|---|---|
| 입력과 출처 | 뉴스레터·공시 등 입력 자료, 출처 URL과 본문 버전 | 어느 자료에서 가져온 사실인지 확인 |
| 사실 | 대상·기간·수치·기준일·조건, 사실 번호와 값의 버전 | 노트에 값을 불러오고 판단의 근거로 참조 |
| 사용처 | 실행 회차, 문서 종류·위치, 참조한 사실 버전 | 어떤 노트·주문·보유·배분 판단이 이 사실을 썼는지 확인 |
| 교정과 재검증 | 이전 값·새 값·교정 사유, 이전 판의 스냅샷 | 옛 값을 본 판정을 새 값의 판정으로 재사용하지 않음 |

출처와 본문 버전은 `ev_source`·`ev_source_version`, 사실은 `ev_fact`와 종류별 상세 표, 이전 값은 `ev_fact_version`에 있습니다. `ev_claim_ref`는 사실 번호와 문서의 사용 위치를 연결합니다. 주문 제안·보유·배분의 근거도 별도 관계로 연결됩니다. [DB 정의](../ai-trading-bot/db_schema.sql)

## 첫 설계를 돌려보낸 이유

출처 검증에서 사실을 고쳐도 분석 노트와 주문안에 이전 내용이 남는 일이 반복됐습니다. 저는 10월 7일 감사에서 반복되는 오류를 단계별 검사에 넣도록 요구했습니다. 질문을 추가한 뒤에도 누락은 이어졌습니다.

AI는 10월 13일 관련 문서를 직접 대조하는 프로그램을 추가했습니다. 이후 실행에서 제출 전 누락 3건을 찾았습니다. 누락을 발견한 것은 확인했지만 재발이 없어졌다고 볼 수는 없었습니다.

10월 17일에는 제가 사실과 데이터를 한곳에서 관리하고, 같은 자료를 다시 조사·검증하는 일을 줄이자고 했습니다. AI는 조사·판단·맥락 해석을 맡고, 프로그램은 사실의 저장과 연결을 맡도록 역할을 정했습니다.

저장 위치만 바꾸는 것으로는 부족했습니다. AI의 첫 설계에는 시장·산업·기업별로 무엇을 조사하고 그중 어떤 항목을 판단에 쓰는지가 드러나지 않았습니다. 다음 요구를 반영하도록 설계안을 돌려보냈습니다.

| 처음 설계에서 부족했던 것 | 제가 요구한 변경 | 현재 구현에서 확인할 부분 |
|---|---|---|
| 조사 결과를 문장과 값 중심의 공통 형식으로 저장 | 조사 종류마다 필요한 항목과 그 항목을 쓰는 판단을 정할 것 | 기업 실적·거시 발표·정책 등 종류별 항목, 사실 번호와 판단의 연결 |
| 뉴스레터·공시 등 입력 자료를 저장할 항목이 빠짐 | 뉴스레터 발행분과 공시 등 입력 자료도 포함할 것 | 입력 자료와 조사한 사실을 연결하는 기록 |
| 기존 자료를 빠짐없이 옮겼는지 알 수 없음 | 코드에서 데이터 종류를 세고 기존 위치와 새 위치를 대조할 것 | 데이터 이전 도구와 이전 전후 내용 비교 |

AI는 이 요구를 바탕으로 데이터베이스와 참조·교정 기능을 구현했습니다. 현재 노트의 수치는 저장한 사실에서 불러옵니다. 사실을 고치면 이전 값도 버전 번호와 함께 보관하고, 그 값을 사용한 판정은 재검증 대상으로 표시합니다. 숫자를 문서마다 고쳐 옮기는 작업을 줄이고 어떤 판단이 그 사실을 썼는지 찾을 수 있게 했습니다. 이 저장 방식은 투자 업무에 적용했습니다.


## 값을 바꾸면 이전 판정은 어떻게 됩니까

다음은 구현 관계를 설명하는 **가상 예시**입니다. 회사 A의 매출 전망을 사실 F로 등록하고, 분석 노트와 매수 제안이 F의 1판을 참조했다고 가정합니다.

1. 전망 값을 정정하면 `_bump`가 변경 전 사실의 머리·세부 항목을 보존하고 교정 사유를 남깁니다.
2. 실제 값이 바뀌면 `value_rev`가 올라갑니다. 단순 표기 편집에 쓰는 `rev`와 구분합니다.
3. `add_ref`가 남긴 문서 위치와 `order_basis`가 모은 주문·보유·배분의 근거를 통해 사용처를 찾습니다. 검증 요청에는 `uses`와 `fact_rev`가 포함됩니다.
4. 현재 값보다 오래된 판정은 새 값의 유효한 판정으로 세지 않습니다. `grade_rows`는 해당 상태를 `REVERIFY`로 반환합니다. 매수 전에는 재검증을 요구하며, 체결 후에는 값이 바뀌었다는 이유만으로 곧바로 소급 매도하지 않고 재확인·재판정 대상으로 넘깁니다.

[사실 등록·참조·교정 코드](../ai-trading-bot/facts.py)의 `_snapshot`, `_bump`, `add_ref`, `order_basis`, `_queue_row`, `grade_rows`가 각 역할을 맡습니다. 잘못된 근거라는 판정과 판정이 낡아 다시 봐야 하는 상태를 구분한 것입니다. 이 예시에서 실제 매매나 수익이 발생했다는 의미는 없습니다.

## 참인 사실도 지금의 판단에 맞는지 확인합니다

12개월 뒤의 목표가를 며칠 안의 투자 판단에 그대로 쓰면 숫자는 맞아도 근거의 적용이 잘못될 수 있습니다. 저는 목표가의 예상 기간과 투자 판단 기한을 함께 보도록 요구했습니다. 원문에 있는 ‘예상’·‘잠정’·적용 대상 같은 조건도 지워서는 안 됩니다.

[검증 기준](05_검증과_개선.md#근거의-조건과-사용-목적을-함께-확인합니다)은 사실 자체와 쓰임을 나눠 설명합니다. 프로그램은 버전·참조·필수 항목을 대조하고, 원문 해석과 판단의 적합성은 AI가 검토합니다. 연결된 데이터가 있다고 판단까지 자동으로 옳아지는 것은 아닙니다.

## 원본을 옮긴 뒤에도 대조할 수 있게 합니다

첫 설계 검토에서 저는 기존 코드가 쓰는 데이터 종류와 이전 전후 내용을 비교하도록 요구했습니다. [이전 도구](../ai-trading-bot/migrate.py)와 [기술 안내](../ai-trading-bot/README.md)는 저장 구조를 확인할 공개 근거입니다. 실제 비공개 원장을 이 문서에서 다시 이전하거나 누락률을 재측정한 것은 아닙니다.

확인한 변화는 교정 이력과 사용처를 추적하고 낡은 판정을 재검증할 수 있는 구현입니다. 모든 사본의 오류 제거, 모든 주문의 자동 수정, 오류율·조사 시간의 정량 개선은 이 근거로 주장하지 않습니다.
