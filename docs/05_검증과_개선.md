# 검증과 개선 — 오류를 고치고 재발 원인을 찾습니다

[포트폴리오](../README.md) / 검증과 개선 · [생태계 설계](01_전체_흐름과_역할.md)

조사한 내용을 제때 믿고 쓸 수 있어야 일을 맡기는 의미가 있습니다. 잘못된 사실로 투자하거나, 설명이 빠진 노트를 받아 제가 다시 조사하면 위임하려던 목적을 이루기 어렵습니다. 반대로 검토가 길어져 주문 시점을 놓치면 확인 절차 자체가 일을 막습니다.

저는 오류가 어디서 생겼는지와 결과를 언제 써야 하는지를 보고 작업 방식을 바꾸도록 요구했습니다. 검사 위치를 앞당긴 경우도 있고, 추가 감사를 주문 뒤로 나눈 경우도 있습니다. 같은 사실의 교정이 계속 누락됐을 때는 검사 추가를 멈추고 저장 구조를 바꿨습니다.

이 문서는 검토 과정에서 발견한 문제와 지침·도구를 수정한 사례를 다룹니다. 목적과 변경 기준은 제가 정했고, 원인 분석과 도구 구현은 AI가 맡았습니다. 매매 관련 사례는 10월 17일까지의 모의투자 기록입니다.

## 주문 전 확인과 주문 후 감사

투자 판단은 근거가 정확해야 하고, 실행할 때도 유효해야 합니다. 감사를 오래 반복하면 작성한 내용은 더 살필 수 있지만 그사이 가격과 상황이 달라집니다. 검토할 내용을 언제 확인해야 하는지 나눌 필요가 있었습니다.

당시 기록에는 반복 감사에 실행당 최대 10시간을 썼다고 적혀 있습니다. 9월 29일 미국 시장 실행에서는 감사가 22번 불통과했지만, 주문을 바꾼 지적은 없었습니다. 10월 13일에는 주문 전 감사가 약 5시간 이어져, 제안된 주문이 모두 유효시간 초과로 거부됐습니다. 이미 확인한 매수 근거 외의 설명을 검토하는 동안에도 주문은 기다리고 있었습니다.

저는 주문 근거의 확인은 먼저 끝내고, 그 판정을 다시 검토하는 감사는 주문 뒤에도 이어가도록 했습니다. AI는 주문에 필요한 근거 판정과 결정 기록을 만들고, 프로그램은 판정 기록이 없거나 확인된 근거가 남지 않은 매수를 거부합니다. 후속 감사는 실행을 마치기 전에 반영합니다.

후속 감사에서 매수 근거가 성립하지 않는 것으로 바뀌면 해당 매수분을 매도합니다. 장이 열려 있으면 같은 실행에서, 닫혀 있으면 다음 해당 시장 실행에서 처리합니다. 그 사이 발생한 가격 변동과 거래 비용은 남습니다. 사후 검토로 주문 전의 모든 위험을 없앨 수 있는 것은 아닙니다.

10월 15일에도 저는 감사 기준을 느슨하게 하지 말고 작성 단계에서 제대로 조사하고 설명하도록 요구했습니다. 반복되는 오류는 여러 실행의 기록을 모아 원인을 찾고 작성 지침과 검사에 반영합니다. 필요한 설명을 준비하지 않은 채 초안을 쓰던 문제에는 [작성 순서를 바꾸는 방식](#writing-order)으로 대응했습니다.

감사 횟수와 반영 범위도 대상별로 다릅니다. 10월 7일 정한 배경 설명의 감사는 최대 두 번이며, 두 번째 결과는 추가 수정 없이 기록합니다. 주문 근거 감사는 최대 다섯 번이고 매수 근거가 뒤집히면 실행 결과에 반영합니다. 배경 설명과 주문 근거의 정책을 하나로 적용하지 않습니다.

현재 확인한 것은 검토 시점과 처리 규칙을 바꿔 지침과 코드에 반영한 것까지입니다. 변경 전후의 전체 처리 시간이나 판단 정확도를 같은 조건에서 비교한 것은 아닙니다. [감사 지연과 변경 지시](../.claude/skills/trade-run/references/stage5_decide.md#L93-L106) · [감사 대상별 정책과 과거 실행 기록](../.claude/skills/trade-run/references/stage4_note.md#L589-L664)

### 업무별 감사 시점

단계 검사를 통과한 산출물도 별도 AI가 다시 읽습니다. 이 검토를 감사라고 부릅니다. 반복해서 발견한 오류는 이후 검사에 반영할 후보로 기록합니다.

감사를 모두 기다리면 결과를 사용하는 시점이 늦어질 수 있어 업무별로 대기와 반영 범위를 정했습니다.

| 업무 | 먼저 끝내야 할 확인 | 후속 감사 |
|---|---|---|
| 학습 노트 | 추가 사실의 출처 검증, 사전 검토와 교정, 발행 전 단계 검사 | 발행 뒤 필요한 사실 교정을 한 차례 반영. 형식·문체 지적은 반복 여부를 기록 |
| 투자 주문 | 매수 근거의 출처 판정과 주문 규칙 | 실행 마감 전 결과 반영. 근거가 성립하지 않는 매수는 매도 |
| 투자 배경 설명 | 분석과 검증·감사를 병행 | 마감 때 확인하고 정해진 대기 뒤에도 결과가 없으면 미수신 기록 |
| 조사 보고서·인터뷰 기록 | 단계별 검사 | 진행 중인 별도 검토가 끝나고 통과했는지 최종 발행 전에 확인 |

문서를 발행하는 AI는 검토 결과가 도착했는지와 통과 여부를 확인합니다. 인터뷰 기록은 작성 전에 제가 구조 초안을 확인하는 절차도 있습니다. 투자의 주문 전 확인과 이후 감사를 나눈 이유는 [앞 절](#주문-전-확인과-주문-후-감사)에서 설명했습니다.

## 작업 단계별 검사

### 각 단계에서 확인하는 내용

초기에는 투자 분석 노트를 작성한 뒤 한 번 검사했습니다. 그런데 같은 날 자료를 다시 수집하면서 뉴스레터가 포함된 파일을 덮어써, 약 58KB였던 자료가 4.8KB로 줄어든 일이 있었습니다. 그 자료로 분석을 시작한 뒤에는 완성 노트만 검사해도 무엇이 빠졌는지 찾기 어려웠습니다. 이전 판단을 읽지 않고 새 분석을 시작한 문제도 마지막 검사에서 놓쳤습니다. 당시 이 문제들은 제가 결과를 읽다가 발견했습니다.

이후 검사를 작업 단계 사이에 두었습니다. 수집 직후에는 재료의 누락을, 이전 판단을 읽은 뒤에는 대기 조건을, 주문 뒤에는 체결과 잔량을 확인합니다. 투자 판단이 맞았는지는 이후 결과를 보고 별도로 평가합니다.

| 시점 | 확인할 것 |
|---|---|
| 자료 수집 후 | 필수 자료의 누락 |
| 이전 판단 확인 후 | 대기 조건과 재검토 항목 |
| 추가 조사 후 | 산업·기업 간 관계와 조사 내용의 분석 반영 여부 |
| 분석 노트 작성 후 | 판단의 근거·조건·출처 |
| 주문 또는 보류 결정 후 | 주문 규칙, 매도 조건, 보류 이유 |
| 주문 결과 확인 후 | 체결과 잔량 처리, 다음 실행에 필요한 기록 |

주문하지 않는 날에도 보류 이유를 검사합니다. 같은 판단을 반복해서 유지해도 되는지 평가하려면 당시 이유와 기다리는 조건이 있어야 합니다.

### AI의 답변을 파일과 대조합니다

AI는 검사 질문에 답하면서 근거 파일과 해당 문장을 인용합니다. 프로그램은 직전 단계의 통과 기록, 산출 파일, 인용문과 필수 항목을 확인합니다. 실패하면 다음 단계로 진행하지 않고, 통과하면 기록을 남깁니다. 주문 전송 프로그램도 필요한 통과 기록을 직접 확인합니다.

작업 AI에게는 질문만 제공하고 상세 판정 기준은 별도 파일에 둡니다. 기준 파일 열람은 운영 규칙으로 금지하지만 같은 파일 시스템에 있어 기술적으로 차단된 것은 아닙니다.

### 주문 접수와 체결을 따로 확인합니다

지정가 주문이 접수됐지만 체결되지 않은 상태를 매수 완료로 보고한 일이 있었습니다. 이후에는 실제 체결 수량과 남은 주문의 취소·만료까지 확인하도록 했습니다.

다음은 [가상 주문 사례](../examples/가상_사례_판단_과정.md#체결-확인)입니다.

| 상태 | 확인할 내용 |
|---|---|
| 12주 매수 주문 접수 | 체결 수량과 남은 주문 |
| 8주 체결, 4주 미체결 | 체결분을 보유 기록에 반영하고 잔량 처리 |
| 나머지 4주 취소 확정 | 취소를 기록하고 다음 실행에서 잔량을 검토할 근거 보존 |

이 상황은 설명을 위한 가정이며 실제 주문 결과는 아닙니다. 현재 실행은 모든 주문의 체결·부분체결·취소·만료·거부 상태를 확인해야 끝납니다.

### 중단한 작업을 다시 실행할 때

투자 실행은 단계별 성공·축소·실패를 기록합니다. 필수 자료 수집에 실패하면 멈추고, 선택 자료를 얻지 못하면 분석 노트에 제한 사항을 적습니다. 주문 제안과 승인에도 유효시간을 둡니다.

전송 도중 작업이 멈추면 다시 실행할 때 그날의 주문 기록부터 읽습니다. 이미 접수된 주문은 다시 보내지 않습니다. 응답을 잃은 주문은 당일 주문 목록에서 상태를 확인한 뒤 다음 조치를 합니다.

## 반복 오류를 찾기 위해 감사 기록을 보관합니다

자체 점검을 마친 결과물에서도 별도 감사가 한정어를 빠뜨린 인용, 원문으로 확인하지 않은 값, 교정을 반영하지 않은 문장을 발견했습니다. 10월 7일 저는 반복되는 오류를 다음 실행의 검사 기준에 반영하도록 요구했습니다.

그러려면 여러 실행의 지적을 함께 볼 수 있어야 했습니다. 당시 감사 결과는 임시 대기열에만 남았고, 실행을 정리하면 없어졌습니다. 매번 문제를 발견하면서도 같은 문제가 얼마나 반복됐는지 확인할 기록이 부족했습니다. AI는 감사에서 발견한 문제를 유형별로 따로 저장하도록 고쳤고, 과거 지적도 추가했습니다.

작성한 AI와 별도로 결과물을 검토하는 스킬이 `gate-audit`입니다. 문제가 있다고 본 문장을 인용하고 유형별로 기록합니다. 프로그램은 그 기록을 보존하고, 서로 다른 두 실행 이상에서 같은 유형이 나오면 검사 보강 후보로 표시합니다. 후보가 생기면 작업 방법을 고치는 스킬인 `skill-maintainer`에서 기존 기준과 원인을 검토해 수정합니다. 감사가 즉시 스킬을 자동 수정하는 구조는 아닙니다.

단계별 검사와 감사도 역할을 나눴습니다. 단계 검사는 그 시점에 필요한 자료와 조건을 갖췄는지 확인하고, 별도 감사는 산출물을 다시 읽어 놓친 문제를 찾습니다. 감사 결과를 언제까지 기다리고 어디까지 반영할지는 [업무별로 정했습니다](#업무별-감사-시점).

공개 지침의 [감사 기록 방식](../.claude/skills/gate-audit/SKILL.md)과 [학습 스킬의 10월 7일 사례](../.claude/skills/world-study/SKILL.md#L66-L93)에서 이 연결을 확인할 수 있습니다. 별도 검토도 AI의 판단이므로 근거와 인용을 확인해야 합니다.

## 출처 검증 기준을 한곳에서 관리합니다

학습 노트와 투자 분석에는 문장의 수치와 조건을 원문과 대조하는 출처 검증 스킬 `fact-check`를 함께 사용합니다. 그런데 이 스킬이 만든 판정표의 품질 기준은 호출하는 업무에 따로 복제돼 있었습니다. 이렇게 두면 한쪽에서 기준을 고쳐도 다른 쪽에 옮겨야 하고, `fact-check`를 직접 호출한 작업에는 그 검사를 적용하지 못합니다. 10월 8일 저는 일반 검증과 투자용 검증을 다르게 설정하는 것이 맞는지 문제를 제기했습니다.

AI는 판정표의 품질 기준을 `fact-check`에 모으고, 이를 호출하는 스킬의 지침과 검사 파일도 수정했습니다. 학습 쪽에는 설명이 충분한지와 교정이 반영됐는지를 확인하는 기준을, 투자 쪽에는 판단과 주문에 필요한 기준을 남겼습니다.

| 확인할 내용 | 기준을 둘 곳 | 이유 |
|---|---|---|
| 인용이 실제 판정을 뒷받침하는가, 조건·한정어를 보존했는가 | `fact-check` | 어느 업무에서 요청해도 판정표에 필요한 품질 |
| 교정이 노트에 반영됐고 원인·개념 설명이 충분한가 | `world-study` | 읽고 이해할 결과물을 만드는 업무의 기준 |
| 주문에 사용할 근거 판정과 실행 조건이 갖춰졌는가 | `trade-run`과 주문 검사 | 투자 판단을 실행으로 옮길 때 필요한 기준 |

공통 기준을 쓴다고 저장 방식과 승인 정책까지 같아지는 것은 아닙니다. 학습은 문서로, 투자는 데이터베이스의 사실·판정 기록으로 검증 결과를 사용합니다. 주문 전 판정과 발행 후 감사의 처리 시점도 다릅니다. [fact-check의 적용 범위와 호출자별 정책](../.claude/skills/fact-check/SKILL.md)

<a id="maintenance"></a>
## 작성 절차와 공통 도구도 고칩니다

결과물을 고치는 일과 작업 규칙을 바꾸는 일은 별도로 진행합니다. 규칙을 바꿀 때는 `skill-maintainer`의 절차를 따릅니다. 기존 목적과 지침을 읽고 오류의 원인을 찾은 뒤, 어느 스킬이나 도구를 고칠지 정합니다. 수정하는 부분을 참조하는 다른 지침과 도구도 확인합니다.

작업을 수행하는 AI가 자기 검사를 통과하려고 실행 도중 기준을 바꾸지는 않습니다. 검사에서 나온 지적은 현재 결과물을 고칠 근거이고, 규칙 변경은 별도 유지보수 절차에서 다룹니다. 아래는 작성 순서와 스킬의 위치, 데이터 저장 방식을 바꾼 사례입니다.

<a id="writing-order"></a>
### 초안을 쓰기 전에 설명할 내용을 조사합니다

학습 노트에는 원인 대신 관련 사실만 붙거나, 용어의 뜻은 있지만 왜 그런 제도가 생겼는지 빠진 항목이 있었습니다. 9월 15일 관계도·오타·부정확한 문장이 발견됐을 때 저는 해당 문장만 고치지 말고 원인을 찾아 스킬을 고치도록 했습니다. AI는 정해 둔 증상만 확인하고 처음 읽는 사람의 입장에서 다시 읽는 절차를 건너뛴 점을 확인했습니다.

이후 검사를 보강했어도 부족한 설명이 감사에서 반복됐습니다. 10월 14일에는 작성 전에 항목별로 사실·원인·개념·예외·사건일을 채우도록 순서를 바꿨습니다. 필요한 설명을 조사하지 않은 채 문장을 쓰고 나중에 찾아 보완하는 부담을 줄이려는 변경입니다.

현재 `world-study`는 먼저 원문과 연결 자료를 읽어 항목별로 설명할 내용을 정리한 뒤 초안을 씁니다. 작성한 AI는 원자료를 모르는 독자도 이해할 수 있는지 다시 읽으며 확인합니다. 프로그램은 설명이 빠졌을 가능성이 있는 문장과 작업용 약칭 등을 표시하고, AI가 보완할 필요가 있는지 판단합니다. [현재 작성 순서](../.claude/skills/world-study/SKILL.md#L18-L43)

### 공통 감사 스킬을 찾지 못한 문제

별도 감사 스킬이 리서치 업무 폴더에 있었을 때는 개인 프로젝트의 출처 검증 스킬이 감사를 호출해도 해당 스킬을 찾지 못했습니다.

AI는 `gate-audit`을 공통 위치로 옮겼습니다. 현재 유지보수 지침은 특정 업무의 산출물을 만드는 스킬과 다른 스킬을 검토·수정하는 스킬의 위치를 구분합니다. 공통 검토·수정 절차는 여러 업무에서 찾을 수 있는 곳에 두고, 업무별 기준은 해당 업무에 남깁니다. [스킬의 배치 기준과 실제 사례](../.claude/skills/skill-maintainer/SKILL.md#L46)

### 스킬 이름을 바꾸면서 검사 파일의 참조를 놓쳤습니다

개인 프로젝트용 지식지도 스킬의 이름을 `knowledge-map`에서 `life-map`으로 바꾸면서 검사 파일의 참조를 함께 바꾸지 않아 정식 검사가 작동하지 않았습니다. 스킬 이름으로 검사 파일을 찾는 구조였기 때문입니다. 정합성 검사 도구가 이 누락을 발견했습니다.

현재 유지보수 지침은 이름·위치를 바꾸면 폴더와 이름 표기, 호출 경로, 검사 파일과 자매 스킬의 참조까지 확인하도록 합니다. 공통 도구는 복사본을 늘리지 않고 원래 엔진을 함께 쓰게 합니다. `knowledge-map`과 `life-map`이 같은 폴더 탐색 도구를 사용하는 것도 이 원칙의 적용입니다.

이 사례의 누락 원인을 분석하고 검사 도구를 보완한 것은 AI입니다. [이름 변경 절차와 실제 사례](../.claude/skills/skill-maintainer/SKILL.md#L91-L104) · [연결 검사 도구](../.claude/skills/_shared/check_skill_integrity.py)

<a id="교정한-사실이-다른-문서에는-남아-있던-문제"></a>
### 사실을 바로잡아도 다른 문서에는 이전 내용이 남았습니다

출처 검증에서 사실을 고쳐도 분석 노트와 주문안에 이전 내용이 남는 일이 반복됐습니다. 저는 10월 7일 감사에서 반복되는 오류를 단계별 검사에 넣도록 요구했습니다. 질문을 추가한 뒤에도 누락은 이어졌습니다.

AI는 10월 13일 관련 문서를 직접 대조하는 프로그램을 추가했습니다. 이후 실행에서 제출 전 누락 3건을 찾았습니다. 누락을 발견한 것은 확인했지만 재발이 없어졌다고 볼 수는 없었습니다.

10월 17일에는 제가 사실과 데이터를 한곳에서 관리하고, 같은 자료를 다시 조사·검증하는 일을 줄이자고 했습니다. AI는 조사·판단·맥락 해석을 맡고, 프로그램은 사실의 저장과 연결을 맡도록 역할을 정했습니다.

저장 위치만 바꾸는 것으로는 부족했습니다. AI의 첫 설계에는 시장·산업·기업별로 무엇을 조사하고 그중 어떤 항목을 판단에 쓰는지가 드러나지 않았습니다. 다음 요구를 반영하도록 설계안을 돌려보냈습니다.

| 처음 설계에서 부족했던 것 | 제가 요구한 변경 | 현재 구현에서 확인할 부분 |
|---|---|---|
| 조사 결과를 문장과 값 중심의 공통 형식으로 저장 | 조사 종류마다 필요한 항목과 그 항목을 쓰는 판단을 정할 것 | 기업 실적·거시 발표·정책 등 종류별 항목, 사실 번호와 판단의 연결 |
| 뉴스레터·공시 등 입력 자료를 저장할 항목이 빠짐 | 뉴스레터 발행분과 공시 등 입력 자료도 포함할 것 | 입력 자료와 조사한 사실을 연결하는 기록 |
| 기존 자료를 빠짐없이 옮겼는지 알 수 없음 | 코드에서 데이터 종류를 세고 기존 위치와 새 위치를 대조할 것 | 데이터 이전 도구와 이전 전후 내용 비교 |

AI는 이 요구를 바탕으로 데이터베이스와 참조·교정 기능을 구현했습니다. 현재 노트의 수치는 저장한 사실에서 불러옵니다. 사실을 고치면 이전 값도 버전 번호와 함께 보관하고, 그 값을 사용한 판정은 재검증 대상으로 표시합니다. 숫자를 문서마다 고쳐 옮기는 작업을 줄이고 어떤 판단이 그 사실을 썼는지 찾을 수 있게 했습니다. 이 저장 방식은 투자 업무에 적용했습니다.

### 수정할 때 확인하는 것

AI에게 개선안과 구현까지 맡기면 한 번의 수정이 다음 과제의 작업 기준이 됩니다. 바꾸려던 부분이 나아졌는지와 함께, 기존 목적과 다른 스킬의 동작을 해치지 않는지도 확인해야 합니다.

`skill-maintainer`는 기존 지침을 읽고 변경 범위를 정한 뒤, 수정 전 상태 보존·전후 내용 대조·관련 테스트와 참조 경로 확인을 거치도록 합니다. 스킬의 문안과 구조를 바꿀 때는 제가 확인하는 것이 기본입니다.

투자 주간 피드백에서는 판단 규칙 보완·도구 오류 수정·매매 대상 추가 중 정해 둔 범위에 한해 사전에 자동 변경을 허용했습니다. 이 경우에도 스킬 수정 절차와 검증을 거칩니다. 안전장치·수치 기준 변경이나 기존 규칙 삭제 등 승인 대상이 함께 들어 있으면 승인을 우선합니다. 자동 변경의 범위는 제가 정하고, 개별 개선안과 구현은 AI가 맡습니다. 다른 업무에는 이 주간 자동 변경 정책을 적용하지 않습니다. [변경 권한과 평가](04_투자_판단과_평가.md#자동-변경과-승인)

#### 테스트를 통과했는데 주문 전송이 실패한 사례

10월 12일 코드를 수정하면서 증권사 호출 결과를 저장하는 한 줄이 빠졌습니다. 문법 검사와 기존 테스트 130건은 통과했지만 다음 실행에서 주문 전송이 실패했습니다. AI가 사고를 분석한 결과 해당 함수를 호출하는 테스트가 없었습니다.

이후 AI는 사라진 코드와 사용되는 변수를 대조하는 검사, 가짜 증권사 연결로 주문 전송부터 체결 확인까지 실행하는 테스트를 추가했습니다. 같은 줄을 다시 지웠을 때 새 테스트 11건 중 6건이 실패했고, 줄이 있는 상태에서는 모두 통과했습니다. 기존에 놓쳤던 이 누락을 새 테스트가 찾는지 확인한 결과입니다.

테스트가 중간에 멈추는 일을 막고 완료 여부를 기록하도록 한 것은 사고 전인 10월 11일 제가 요구한 사항입니다. 사고 후 검사와 실행 경로 테스트의 보강은 AI의 분석으로 이루어졌습니다.

## 출처를 확인하고 판정하는 기준

### 출처에서 무엇을 확인하는가

`fact-check`는 링크가 열리는지, 원문에 해당 주장을 뒷받침하는 내용이 있는지, 지금도 유효한 정보인지, 그 사실을 확인하기에 적절한 출처인지를 봅니다.

| 판정 | 의미와 조치 |
|---|---|
| 일치 | 원문이 문장의 수치·조건·범위를 뒷받침하므로 근거로 사용 |
| 불일치 | 내용이나 적용 조건이 달라 문장을 고치거나 판단에서 제외 |
| 시효 지남 | 현재 판단에 그대로 쓰기 어려워 최신 자료 확인 |
| 확인 불가 | 자료 접근이나 근거 확인이 어려운 이유를 적고 미확인 상태로 보존 |

이 네 가지는 학습·투자에서 사용하는 `fact-check`의 판정입니다. 완성 리서치 문서를 감리하는 `research-source-check`는 일치·불일치·확인 불가의 세 가지를 사용합니다. 공통된 원칙은 확인할 수 없는 정보와 틀린 정보를 다르게 처리하는 것입니다. 출처도 해당 내용을 직접 발표·기록한 자료와 이를 전한 보도·분석으로 구분합니다.

[가상 정책 사례](../examples/컨설팅_가상_사례.md#잘못-인용한-문장을-고치는-경우)에서는 뉴스레터의 ‘2027년부터 60%’를 원문의 ‘2027년 40%, 2028년 60%’와 대조합니다. 60%라는 숫자가 원문에 있어도 적용 연도가 다르므로 불일치입니다.

### 사실과 해석의 표시

학습 노트에서는 원문에 없는 사실·제도 설명에 `[AI]`, 원인이나 의도에 대한 해석에 `[추정]`을 붙입니다. 원문 각주와 연결 자료를 먼저 확인하고, `[AI]` 문장은 발행 전에 출처와 대조합니다.

리서치에서는 원문을 확보하고 보고서의 주장을 하나씩 다시 확인합니다. 출처 목록에는 인용문과 사용한 곳을 적습니다. 반박 자료가 있으면 기존 근거를 재검토하고, 완성 문서를 감리할 때는 원문을 직접 고치는 대신 교정 지시서를 냅니다.

## 기록별 보관 위치

| 남길 내용 | 기록할 곳 |
|---|---|
| 개인적인 선호와 반복되는 교정 | 메모리 |
| 같은 유형의 과제에도 적용할 작업 기준 | 스킬과 관련 도구 |
| 이번 과제의 결정·이유·확인 결과 | 변경 기록 |
| 결과물 위치·진행 상태·이어 할 일 | 지식지도 |

메모리는 다음 작업에 필요한 맥락을 떠올리는 데 사용합니다. 실제 수행해야 할 절차는 스킬에 넣습니다. 지식지도에서는 자료의 위치를 안내하며, 스킬을 호출했을 때 갱신합니다. 상세 근거와 버전별 변경 내용은 해당 과제의 파일에서 확인합니다.

조사 업무에서는 문서에 원문 이미지를 넣는 반복 작업을 작성 도구에 반영하고, 학습에서는 설명이 빠진 이유를 분석해 작성·검토 기준을 고쳤습니다. 투자에서는 판단과 실행 결과를 저장해 다음 실행과 평가가 읽게 했습니다. [리서치 사례](02_리서치_분석_보고서.md) · [학습 사례](03_학습노트_설계.md) · [투자 사례](04_투자_판단과_평가.md)

## 확인 범위와 한계

프로그램은 파일·인용문·필수 항목·수치 조건을 대조합니다. 주장이 문맥에 맞는지, 설명이 충분한지, 투자 근거가 타당한지에는 AI와 사람의 판단이 들어갑니다. 기록이 남았다는 사실만으로 내용의 정확도를 보장하지 않습니다. 검사 절차를 호출하지 않은 작업을 모두 막을 수도 없습니다.

외부 뉴스레터와 공시는 분석 자료로 사용합니다. 종목 권유나 설정 변경 지시가 들어 있어도 실행 명령으로 받아들이지 않습니다. 매매 대상 밖의 종목은 편입 후보로 따로 검토합니다. 공통 검사 도구를 사용하더라도 각 업무가 같은 데이터베이스나 동일한 승인 절차를 쓰는 것은 아닙니다.
