# 스킬 운영 원칙 — 공통 방법의 재사용과 업무별 절차

컨설팅 리서치에서 사용하던 출처 검증 방법과 작업 검사 절차를 학습 노트와 투자에도 적용했습니다. 업무별로 필요한 결과물과 처리 시점은 달랐지만, 근거를 확인하고 필요한 절차가 수행됐는지 기록으로 점검하는 방법은 함께 사용할 수 있었습니다. 이 글은 현재 어떤 방법을 공유하고 어떤 절차를 업무별로 따로 두는지, 스킬을 고칠 때 어떤 절차와 승인을 거치는지 설명하고, 그 기준을 정하게 된 사례를 뒤에 두었습니다.

## 공통 방법과 업무별 절차

| 공통으로 사용하는 방법 | 업무별로 구분한 내용 |
|---|---|
| 자료 조사와 출처 검증 방법 | 일상·실무 조사와 컨설팅·기업 리서치의 담당 스킬 및 조사 범위 |
| 출처와 주장의 대조 | 일반 산출물과 컨설팅 산출물의 검사 항목 |
| 폴더 구조를 읽고 자료의 위치·요약을 정리하는 방법 | 개인 프로젝트와 컨설팅 과제의 분류 체계 |
| 단계별 검사 엔진 | 각 업무의 검사 항목과 작업 완료 조건 |

공통으로 쓰는 검증 가이드와 일부 프로그램은 한곳에서 관리하고 필요한 스킬이 참조합니다. 각 스킬에는 담당 업무와 다른 스킬을 사용해야 하는 경우를 적었습니다. 컨설팅 자료의 분류 체계는 제가 사용하던 기준을 유지하고, AI가 임의의 체계로 다시 분류하지 않도록 했습니다. 공시 분석의 원본 도구 한 개는 별도 검사 없이 호출되는 공유 도구로 두고, 실행 환경용 스킬이 같은 엔진을 사본 없이 씁니다.

## 감사 결과를 기다리는 시점

감사는 단계 검사를 통과한 산출물을 별도의 AI 에이전트가 정해진 항목으로 다시 읽는 절차입니다. 결과를 언제 기다리고 반영하는지는 업무별로 다릅니다.

| 대상 | 감사 중 진행하는 작업 | 결과를 확인하고 반영하는 시점 |
|---|---|---|
| 학습 노트 | 감사 결과를 기다리지 않고 노트 발행과 보고까지 진행 | 결과가 도착하면 필요한 교정을 한 차례 반영하고 기록. 감사 통과를 기다리며 반복 실행하지 않음 |
| 투자의 주문 근거 | 주문 전 출처 검증과 판정을 마친 뒤, 후속 감사가 끝나기 전에 주문 가능 | 실행을 마치기 전에 감사 결과를 반영. 감사는 최대 5회이며, 체결된 매수의 근거가 성립하지 않으면 해당 매수분을 매도 |
| 투자의 배경 설명 | 검증·감사를 병행하며 다음 작업 진행 | 실행을 마칠 때 결과를 확인. 정해진 대기·재요청 후에도 결과가 없으면 미수신으로 기록 |
| 컨설팅 산출물 | 단계별 검사를 통과한 뒤 감사와 다음 작업을 병행 | 최종 발행·완료 선언 전에 활성 감사의 통과 여부를 확인. 대기 중이면 기다리고, 실패하면 수정 후 다시 감사 |

컨설팅 산출물의 최종 감사 상태는 AI가 실행하는 별도 명령으로 확인합니다. 이 명령은 제가 직접 승인하는 행위와 구분됩니다. 학습 노트와 투자에는 이 최종 확인 명령을 동일하게 적용하지 않습니다.

감사에서 반복해 지적되는 유형은 단계별 검사 항목으로 올립니다. 감사 결과는 항목별로 기록되고, 서로 다른 실행 두 번 이상에서 같은 항목이 걸리면 승격 대기로 표시됩니다. 감사를 통과 조건으로 두면 실행마다 수 시간이 걸렸기 때문에, 감사는 관측으로 두고 반복되는 것만 관문으로 올리는 구조를 택했습니다.

## 스킬을 수정하는 절차와 승인 범위

스킬 문서나 코드를 고칠 때는 편집 전 상태를 보존하고, 편집 전후를 대조해 사라진 줄이 없는지 확인하며, 코드 편집이면 더 이상 쓰이지 않는 변수와 사라진 호출을 검사하고, 관련 테스트와 스킬 간 참조를 다시 확인합니다. 스킬의 문안과 구조를 바꾸는 편집은 제 확인을 거치고, 보호 대상으로 지정한 스킬의 호출 조건을 바꾸는 경우에도 제 승인이 필요합니다. 투자 주간 피드백의 '다음 주 지표로 검증하고 개선되지 않으면 철회' 정책은 그 업무에만 적용하며, 모든 스킬 편집에 주간 지표 검증을 적용하는 것은 아닙니다.

이름을 바꿀 때는 스킬 폴더, 호출 이름, 검사 기준표, 다른 문서의 참조 경로도 함께 확인합니다. 정합성 검사 프로그램이 이름·경로·검사 기준표의 연결과 파일 형식을 확인하지만, 실제 요청에 적절한 스킬이 선택되는지까지 이 검사만으로 판단하지는 못합니다.

작업을 수행하는 AI에 제공하는 지침과 상세 판정 기준은 분리하고, 파일로 확인할 수 있는 항목은 코드가 직접 대조합니다. 다만 검사 호출 자체를 생략한 작업을 모두 차단할 수는 없으며, 판정 기준표도 같은 파일 시스템에 있어 접근이 완전히 차단된 것은 아닙니다. 내용의 타당성을 검토하는 감사 역시 AI의 판단을 포함합니다.

## 기준을 정하게 된 사례

**반복되는 오류를 검사 방식의 개선으로 연결.** 9월 15일에는 특정 사례에만 대응하지 말고 원인을 분석해 스킬 자체를 고치도록 요구했습니다. 10월 7일에는 감사에서 반복적으로 발견되는 오류를 단계별 검사에도 반영하도록 했습니다. 한 사례는 교정한 내용이 다른 문서에 반영되지 않는 문제였습니다. 출처 검증에서 사실을 고쳐도 분석 노트, 주문안, 시장 지도에는 이전 내용이 남아 있었습니다. 10월 7일 관련 검사 질문을 추가했지만 이후 감사에서도 같은 누락이 반복됐습니다. 시스템은 10월 13일 교정 내용과 관련 문서의 사본을 직접 대조하는 프로그램을 추가했고, 10월 15일과 16일 실행에서 이 검사로 제출 전 누락 3건을 발견했습니다. 수행 여부를 묻는 검사에 실제 문서 대조를 추가한 변경이며, 확인된 개선은 누락을 제출 전에 발견할 수 있게 됐다는 점입니다. 10월 17일 투자 시스템이 사실을 데이터베이스에 한 번만 저장하는 구조로 바뀌면서, 투자에서는 교정을 사본에 옮기는 일 자체가 없어졌습니다.

**테스트가 통과했는데 주문 전송이 실패한 이유.** 10월 12일 주문 전송 코드를 수정하는 과정에서 증권사 호출 결과를 저장하는 한 줄이 빠졌습니다. 문법 검사와 기존 테스트 130건은 통과했지만, 다음 날 실행에서는 주문 전송이 실패했습니다. 당시 테스트에는 문제가 생긴 함수를 호출하는 항목이 없었습니다. 사고 분석에서는 스킬 문서에 적용하던 편집 전후의 누락 대조를 코드에는 적용하지 않은 점도 확인됐습니다. 이후 시스템은 코드에서 사라진 줄과 계속 사용되는 변수를 확인하는 검사를 추가하고, 가짜 증권사 연결을 사용해 주문 전송부터 체결 확인까지 실행하는 테스트를 마련했습니다. 10월 16일 재현 검사에서는 문제가 됐던 한 줄을 사본에서 다시 삭제했을 때 주문 실행 경로 테스트 11건 중 6건이 실패했고, 해당 줄이 있는 상태에서는 11건 모두 통과했습니다. 테스트가 중간에 멈추는 일을 방지하고 완료 여부를 기록하도록 한 것은 사고 전인 10월 11일 제가 요구한 사항이며, 사고 이후의 코드 검사와 실행 경로 테스트 보강은 시스템의 분석을 통해 이루어졌습니다.

**정해 둔 절차의 준수.** 9월 1일에는 정해 둔 수정 절차를 거치지 않고 스킬을 편집한 일을 지적했습니다. 9월 9일에는 스킬 설명문의 형식 오류로 다섯 스킬이 도구 목록에서 사라진 일이 있었으며, 이런 형식 오류도 정합성 검사 대상에 포함했습니다.

## 구성과 공개 범위

공개 구성은 일상·투자 스킬 6개, 컨설팅 리서치 스킬 9개, 스킬 수정·감사를 담당하는 스킬 2개입니다. 이 중 16개가 공통 단계 검사 엔진을 사용합니다. 전체 스킬 목록과 검사 지점·참조 관계는 [스킬 구성 참고 자료](reference/스킬_구성.md)에 정리했습니다. 검사 항목의 개수는 구현 규모를 설명하는 값이며, 판단의 정확성이나 오류 감소율을 나타내지는 않습니다.

운영 사례는 기록에서 설계 변경과 결과를 설명하는 데 필요한 내용을 요약했습니다. 원본 운영 기록과 검사·감사 원장은 공개하지 않습니다. 컨설팅 스킬의 조직·고객·과제·인터뷰 대상 식별 정보는 일반어로 바꾸고, 실제 회의록과 내부 서식·디자인 규격은 제외했습니다.
