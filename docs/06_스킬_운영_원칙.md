# 여러 업무에 검증 방법을 재사용하고 보완한 과정

컨설팅 리서치에서 사용하던 출처 검증 방법과 작업 검사 절차를 학습 노트와 모의투자에도 적용했습니다. 업무별로 필요한 결과물과 처리 시점은 달랐지만, 근거를 확인하고 필요한 절차가 수행됐는지 기록으로 점검하는 방법은 함께 사용할 수 있었습니다.

운영 중에는 스킬을 수정하면서 필요한 코드가 빠지거나, 검사에서 지적한 문제가 다음 실행에서도 반복됐습니다. 저는 개별 결과물을 고치는 데서 끝내지 말고 원인을 분석해 스킬을 개선하도록 요구했습니다. 이 글에서는 반복된 오류가 검사 방식의 변경으로 이어진 사례와, 공통 방법을 업무별로 다르게 적용한 과정을 설명합니다.

## 반복되는 오류를 검사 방식의 개선으로 연결

9월 15일에는 특정 사례에만 대응하지 말고 원인을 분석해 스킬 자체를 고치도록 요구했습니다. 10월 7일에는 감사에서 반복적으로 발견되는 오류를 단계별 검사에도 반영하도록 했습니다.

한 사례는 교정한 내용이 다른 문서에 반영되지 않는 문제였습니다. 출처 검증에서 사실을 고쳐도 분석 노트, 주문안, 시장 지도에는 이전 내용이 남아 있었습니다. 10월 7일에는 관련 검사 질문을 추가했지만, 이후 감사에서도 같은 누락이 반복됐습니다.

시스템은 10월 13일 교정 내용과 관련 문서의 사본을 직접 대조하는 프로그램을 추가했습니다. 각 문서에 교정이 반영됐는지 확인하고 누락된 곳을 표시하도록 했습니다. 수행 여부를 묻는 검사에 실제 문서 대조를 추가한 변경입니다.

10월 15일과 16일 실행에서는 이 검사로 제출 전 누락 3건을 발견했습니다. 같은 오류가 다시 발생한 것은 사실이며, 확인된 개선은 그 누락을 제출 전에 발견할 수 있게 됐다는 점입니다.

## 테스트가 통과했는데 주문 전송이 실패한 이유

10월 12일 주문 전송 코드를 수정하는 과정에서 증권사 호출 결과를 저장하는 한 줄이 빠졌습니다. 문법 검사와 기존 테스트 130건은 통과했지만, 다음 날 실행에서는 주문 전송이 실패했습니다. 당시 테스트에는 문제가 생긴 함수를 호출하는 항목이 없었습니다.

사고 분석에서는 스킬 문서에 적용하던 편집 전후의 누락 대조를 코드에는 적용하지 않은 점도 확인됐습니다. 이후 시스템은 코드에서 사라진 줄과 계속 사용되는 변수를 확인하는 검사를 추가하고, 가짜 증권사 연결을 사용해 주문 전송부터 체결 확인까지 실행하는 테스트를 마련했습니다. 코드 수정 후에는 해당 경로를 검사하는 테스트를 다시 실행하도록 편집 절차도 보완했습니다.

10월 16일 재현 검사에서는 문제가 됐던 한 줄을 사본에서 다시 삭제했습니다. 문법 검사는 통과했지만, 주문 실행 경로 테스트 11건 중 6건이 실패했습니다. 해당 줄이 있는 상태에서는 11건 모두 통과했습니다. 기존에 놓쳤던 이 누락을 새 테스트가 발견하는지 확인한 결과입니다.

테스트가 중간에 멈추는 일을 방지하고 완료 여부를 기록하도록 한 것은 사고 전인 10월 11일 제가 요구한 사항입니다. 사고 이후의 코드 검사와 실행 경로 테스트 보강은 시스템의 분석을 통해 이루어졌습니다.

## 감사 결과를 기다리는 시점을 업무별로 구분

모의투자에서는 주문 근거 감사를 기다리는 동안 주문 정보의 유효시간이 지나 제안된 주문이 거부된 일이 있었습니다. 저는 주문 전에 필요한 근거 검증은 수행하고, 감사는 주문 이후에도 이어가도록 변경을 요청했습니다. 자세한 경위는 [정보 검증 문서](01_정보_검증.md)에 정리했습니다.

현재는 업무별로 감사 결과를 기다리는 시점과 후속 조치를 구분합니다.

| 대상 | 감사 중 진행하는 작업 | 결과를 확인하고 반영하는 시점 |
|---|---|---|
| 학습 노트 | 감사 결과를 기다리지 않고 노트 발행과 보고까지 진행 | 결과가 도착하면 필요한 교정을 한 차례 반영하고 기록. 감사 통과를 기다리며 반복 실행하지 않음 |
| 모의투자의 주문 근거 | 주문 전 출처 검증과 판정을 마친 뒤, 후속 감사가 끝나기 전에 주문 가능 | 실행을 마치기 전에 감사 결과를 반영. 감사는 최대 5회이며, 체결된 매수의 근거가 성립하지 않으면 해당 매수분을 매도 |
| 모의투자의 배경 설명 | 검증·감사를 병행하며 다음 작업 진행 | 실행을 마칠 때 결과를 확인. 정해진 대기·재요청 후에도 결과가 없으면 미수신으로 기록 |
| 컨설팅 산출물 | 단계별 검사를 통과한 뒤 감사와 다음 작업을 병행 | 최종 발행·완료 선언 전에 활성 감사의 통과 여부를 확인. 대기 중이면 기다리고, 실패하면 수정 후 다시 감사 |

컨설팅 산출물의 최종 감사 상태는 AI가 실행하는 별도 명령으로 확인합니다. 이 명령은 운영자가 직접 승인하는 행위와 구분됩니다. 학습 노트와 모의투자에는 이 최종 확인 명령을 동일하게 적용하지 않습니다.

## 공통 방법과 업무별 절차를 나누어 관리

출처를 확인하고 조사 자료를 정리하는 방법은 여러 업무에 재사용하되, 업무에 맞는 입력 자료와 결과물은 구분했습니다.

| 공통으로 사용하는 방법 | 업무별로 구분한 내용 |
|---|---|
| 자료 조사와 출처 검증 방법 | 일상·실무 조사와 컨설팅·기업 리서치의 담당 스킬 및 조사 범위 |
| 출처와 주장의 대조 | 일반 산출물과 컨설팅 산출물의 검사 항목 |
| 폴더 구조를 읽고 자료의 위치·요약을 정리하는 방법 | 개인 프로젝트와 컨설팅 과제의 분류 체계 |
| 단계별 검사 엔진 | 각 업무의 검사 항목과 작업 완료 조건 |

공통으로 쓰는 검증 가이드와 일부 프로그램은 한곳에서 관리하고 필요한 스킬이 참조합니다. 각 스킬에는 담당 업무와 다른 스킬을 사용해야 하는 경우를 적었습니다. 컨설팅 자료의 분류 체계는 제가 사용하던 기준을 유지하고, AI가 임의의 체계로 다시 분류하지 않도록 했습니다.

이름을 바꿀 때는 스킬 폴더, 호출 이름, 검사 기준표, 다른 문서의 참조 경로도 함께 확인합니다. 9월 9일에는 스킬 설명문의 형식 오류로 다섯 스킬이 도구 목록에서 사라진 일이 있었으며, 이런 형식 오류도 검사 대상에 포함했습니다.

정합성 검사가 확인하는 범위는 이름·경로·검사 기준표의 연결과 파일 형식입니다. 실제 요청에 적절한 스킬이 선택되는지까지 이 검사만으로 판단하지는 못합니다.

## 스킬을 수정하는 절차와 승인 범위

9월 1일에는 정해 둔 수정 절차를 거치지 않고 스킬을 편집한 일을 지적했습니다. 현재는 편집 전 상태를 보존하고, 편집 전후를 대조하며, 관련 테스트와 스킬 간 참조를 확인하는 절차를 사용합니다.

스킬의 문안과 구조를 바꾸는 편집은 제 확인을 거치도록 했습니다. 보호 대상으로 지정한 스킬의 호출 조건을 바꾸는 경우에도 제 승인이 필요합니다. 모의투자 주간 피드백에서 사용하는 '다음 주 지표로 검증하고 개선되지 않으면 철회' 정책은 별도로 적용합니다. 모든 스킬 편집에 주간 지표 검증을 적용하는 것은 아닙니다.

작업을 수행하는 AI에 제공하는 지침과 상세 판정 기준은 분리하고, 파일로 확인할 수 있는 항목은 코드가 직접 대조합니다. 다만 검사 호출 자체를 생략한 작업을 모두 차단할 수는 없으며, 판정 기준표도 같은 파일 시스템에 있어 접근이 완전히 차단된 것은 아닙니다. 내용의 타당성을 검토하는 감사 역시 AI의 판단을 포함합니다.

## 구성과 공개 범위

공개 구성은 일상·투자 스킬 6개, 컨설팅 리서치 스킬 9개, 스킬 수정·감사를 담당하는 스킬 2개입니다. 이 중 16개가 공통 단계 검사 엔진을 사용합니다. 공시 분석의 원본 도구 한 개는 별도 검사 없이 호출되는 공유 도구로 유지합니다.

전체 스킬 목록과 검사 지점·참조 관계는 [스킬 구성 참고 자료](reference/스킬_구성.md)에 정리했습니다. 검사 항목의 개수는 구현 규모를 설명하는 값이며, 판단의 정확성이나 오류 감소율을 나타내지는 않습니다.

운영 사례는 기록에서 설계 변경과 결과를 설명하는 데 필요한 내용을 요약했습니다. 원본 운영 기록과 검사·감사 원장은 공개하지 않습니다. 컨설팅 스킬의 조직·고객·과제·인터뷰 대상 식별 정보는 일반어로 바꾸고, 실제 회의록과 내부 서식·디자인 규격은 제외했습니다.
